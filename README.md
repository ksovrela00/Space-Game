# Solar Trader

Космический симулятор в духе Elite: полёт от планеты к планете внутри
звёздной системы, стыковка со станциями и посадка на луны. Чистый
JavaScript, ES-модули, WebGL2 (приборы — Canvas 2D поверх), свой движок.
Сборка не нужна.

## Запуск

Зависимостей у игры нет: `npm install` не нужен, сборки тоже. (Сервер —
отдельная история: там есть composer и Ratchet, см. «Игра и сервер».) Нужен
любой HTTP-сервер — ES-модули не работают из `file://`.

Сервер игры (PHP + MySQL) нужен для полёта с другими пилотами и для
входа: у него живут состояние пилота, экономика и ЧИСЛА КОРАБЛЯ.
Поиграть без него можно — `index.html?offline=1`, — и тогда числа
берутся из слепка `server/data/specs.json`, а сохранение остаётся в
браузере.

Если проект лежит в `htdocs` XAMPP, достаточно открыть:

```
http://localhost/space_game/
```

Без XAMPP годится что угодно, например из папки проекта:

```
python -m http.server 8080      # -> http://localhost:8080/
npx serve .                     # -> адрес выведет сам
php -S localhost:8080           # если есть PHP
```

Параметры в адресной строке:

- `?dev=1` — старт в 20 км от порта станции для быстрой проверки стыковки
  (сохранение при этом не читается);
- `?renderer=2d` — принудительно Canvas-2D-рендер вместо WebGL (для сравнения
  картинки и как запасной путь на старом железе);
- `?surface=clipmap` — прежний способ рисовать поверхность (заплатки под
  кораблём с процедурной деталью на каждый пиксель) вместо плиток: полезен
  для сравнения картинки и как запасной путь;
- `?detail=0` — без процедурной детали на пиксель; имеет смысл только
  вместе с `?surface=clipmap`;
- `?fw=N` — закрепить резкость мелкого рельефа вместо регулятора: `1` —
  всегда полная, `8` — всегда самая грубая (см. «Цена кадра»);
- `?scale=0.7` — рисовать сцену в 0.7 от разрешения окна (приборы
  остаются в полном);
- `?aa=0` — без сглаживания краёв.

Серверная часть (см. «Сервер: подготовка к онлайну») поднимается отдельно и
одной командой — нужен запущенный MySQL из XAMPP:

```
npm run api:setup               собрать базу и залить каталог
php server/cli/player.php add <логин> <пароль>    завести пилота
npm run ws                      сокет-сервер (кто где летает), порт 3893
http://localhost/space_game/server/     состояние сервера в браузере
```

Без сервера игра тоже запускается — `index.html?offline=1`.

## Перенос на другую машину

Проект лежит в git с remote на GitHub, поэтому переносится клонированием:

```
git clone https://github.com/ksovrela00/Space-Game.git
```

Положить папку надо туда, откуда её отдаёт HTTP-сервер (в XAMPP это
`htdocs`), либо поднять сервер прямо в ней — см. «Запуск». Сборки нет:
`index.html`, `css/`, `js/` — это всё, что нужно браузеру. `npm install`
тоже не нужен, зависимостей у игры нет; composer-зависимость сервера
(Ratchet) лежит в репозитории готовой, в `server/vendor`.

### Игра с сервером: три команды

Нужен запущенный MySQL из XAMPP. Дальше из папки проекта:

```
npm run api:setup                                 база, таблицы, каталог, числа
php server/cli/player.php add <логин> <пароль>    завести пилота
npm run ws                                        сокет-сервер, порт 3893
```

Первая команда делает всё сама и её **можно гонять сколько угодно раз**:
создаёт базу, если её нет, доводит схему до нынешней версии, заливает
каталог и характеристики корабля. Чужие данные она при этом не трогает —
строки обновляются на месте, а не пересоздаются, иначе заливка уносила бы
склады станций и чьи-то взятые подряды.

Проверить, что получилось: `npm run api:status` — он печатает версию
схемы и число строк в каждой таблице. Состояние сервера видно и в
браузере: `http://localhost/space_game/server/`.

### Миграции идут сами

Схема довозится при каждом `npm run api:setup`
([Schema::migrate](server/src/Schema.php)): недостающие таблицы
создаются, недостающие столбцы добавляются, **лишние сносятся**. Список
на снос заведён отдельно (`Schema::dropped`) и нужен по той же причине,
что и всё остальное: на второй машине в базе уже есть игроки, и
«снести и залить заново» унесло бы их вместе с устаревшим столбцом.

Отсюда правило при работе на двух машинах: **после `git pull`, который
принёс правки схемы или чисел, — `npm run api:setup`**. Версию схемы,
которую ждёт код, видно в `npm run api:status` и в ответе `ping`.

Пересоздать базу с нуля (все игроки пропадут):
`npm run api:setup -- --reset`.

### Если доступ к базе другой

`server/config.php` держит значения локального XAMPP (root, пустой
пароль). Править его не надо: если рядом положить `server/config.local.php`,
он главнее, а в репозиторий не попадёт — он в `.gitignore`.

```php
<?php
define('MYSQLUSER', 'solar');
define('MYSQLPASS', 'секрет');
```

PHP игра ищет сама ([tools/php.mjs](tools/php.mjs)): в `PATH` его обычно
нет, а XAMPP на другой машине лежит по другому пути. Не нашёлся — задать
явно: `SOLAR_PHP=C:/xampp82/php/php.exe`.

### Игра без сервера

`index.html?offline=1` запускается и без PHP с MySQL: числа корабля берутся
из слепка `server/data/specs.json` — это обычный файл, его отдаёт любой
статический сервер. Сохранение при этом местное, соседей по системе нет.

### Что не переносится

- **Сохранение.** Оно в `localStorage` браузера и привязано к домену. С
  сервером это не потеря: состояние пилота лежит в базе, и на новой
  машине достаточно войти под тем же логином.
- **База.** Клонируется код, а не данные. Нужны те же пилоты — переносить
  базу отдельно (`mysqldump`), иначе новая заведётся пустой.
- **Незакоммиченное.** Перед переходом стоит посмотреть `git status`:
  чего нет в remote, того не будет и на новой машине.

### Проверка после переноса

```
npm run check       клиентские наборы (нужен только Node 18+, лучше 20+)
npm run api:test    серверные (на отдельной базе solar_trader_test)
npm run ws:test     сокет
npm run lan         пускает ли брандмауэр на порт 3893 из локальной сети
```

Дальше открыть страницу: в консоли не должно быть ошибок, а на отладочном
оверлее `~` — fps, координаты и строка GPU. Если fps низкий, а GPU-строка
говорит про программный рендер, дело в драйвере, а не в проекте: у
браузера в Windows свой выбор карты (Параметры → Система → Дисплей →
Графика), и на настольной машине карта вообще не участвует, если монитор
воткнут в материнскую плату.

## Статус

Сделано и проверено: полёт с **векторной скоростью и инерцией**, **галактика
из семи звёздных систем** с переходом между ними варп-прыжком, родная
система из девяти планет, семи лун и четырёх станций, **квантовый привод**
(перелёты прыжками с
тоннелем и полосами звёзд), форсаж, ручная стыковка и докинг-компьютер, **посадка на безатмосферные тела** (шасси,
подъёмные движки, посадочный компьютер, стоянка и взлёт), **гравитация тел и
захват**, **удары с отскоком и постепенным разрушением корпуса**, тень корабля
на грунте, приборы подхода, карта системы, **меню пилота** (корабль, груз,
задания, финансы), справка, звук, два вида камеры с осмотром мышью,
сохранение. **Сервер** (PHP + MySQL) держит каталог галактики, экономику и
игроков, и игра с ним уже разговаривает: вход, состояние, сохранение по
сети, сбор за стыковку и платный ремонт. **Сокет** (Ratchet, порт 3893)
показывает, кто ещё летает в этой системе.

Не сделано (сознательно, следующий этап): **экраны станции** — рынок и
доска подрядов сервером уже отдаются, но показать их в игре пока нечем;
чужие корабли видны только отметками на сканере, а не моделями в кадре;
сервер не проверяет движение (физики на нём нет); бои и NPC; посадка на
планеты с атмосферой (нужен аэродинамический спуск).

Пять отступлений от первоначального замысла — их причины важны, если менять
масштабы или динамику:

- вместо ускорения времени сделан **квантовый привод — отдельный режим
  полёта** (`js/game/quantum.js`): мировые часы идут в реальном темпе, поэтому
  планеты не носятся по орбитам, а перелёт всё равно занимает полминуты-минуту.
  Раньше здесь был круизный множитель со ступенями (`T`/`Y`) и mass lock; он
  протекал во все подсистемы разом — в посадочный компьютер, докинг,
  навигацию, нагрев в атмосфере, — и каждую из них приходилось учить жить с
  множителем. Режим не протекает никуда: пока он работает, не работает больше
  ничего;
- **орбитальные периоды — годы**, то есть тела идут по орбитам медленно
  (`js/game/world.js`): планета, обгоняющая корабль, делала бы стыковку
  невозможной — станция убегала бы из-под носа;
- **гравитационный захват вместо орбитальной механики** (`js/game/gravity.js`).
  У каждого тела своя гравитация: масса считается из плотности по типу тела
  (камень 3.3, лёд 1.6, газ 1.3 г/см³) и радиуса, отсюда ускорение на
  поверхности (0.8–6.5 м/с² у здешних тел) и радиус захвата — сфера действия
  a·(m/M)^0.4, урезанная порогом «тяжесть не ниже 0.03 м/с²». Порог нужен
  из-за крупных тел: у газового гиганта одна только сфера действия — четверть
  миллиона километров, и формально корабль «в захвате» там, где до планеты
  двое суток лёта. В итоге захват держится до 5–15 радиусов тела. Внутри захвата корабль
  ПЕРЕНОСИТСЯ вместе с телом: орбитальное движение компенсируется целиком,
  суточное вращение — полностью ниже 8 км над грунтом и плавно сходит на нет
  к 80 км. Это не тяга и не сила, а смена системы отсчёта: иначе «зависнуть
  над точкой» невозможно в принципе — поверхность уезжает из-под корабля со
  скоростью вращения. Так же поступают все игры, где есть посадка;
- **шасси не меняет управление кораблём** — только предел скорости. Раньше его
  выпуск переключал модель полёта целиком: выключался компенсатор высоты
  (корабль начинал проваливаться сам), а главные движки переставали толкать
  вверх и работали только по горизонту. Задумано это было как «почувствовать
  вес на посадке», а читалось как поломка: одна клавиша — и аппарат перестаёт
  слушаться так, как слушался секунду назад. Компенсатор высоты работает
  всегда: он держит и вес, и саму высоту, поэтому с нейтральными ручками
  корабль висит на месте на любой высоте и с любым шасси. Тяжесть от этого не
  исчезла — она задаёт силу подъёмных движков, решает исход удара и работает в
  полную силу, пока корабль оглушён: там нет ни тяги, ни стабилизации, и
  горизонтальный бросок идёт по параболе;
- **периоды суток привязаны к радиусу тела** (20–80 секунд на километр,
  то есть от 7 до 130 часов): скорость поверхности выходит 0.1–0.3 км/с, как
  у настоящих планет. Раньше периоды были в сотни раз короче — вращение
  красиво читалось с орбиты, но поверхность «ехала» со скоростью в десятки
  км/с, и сесть на неё было физически невозможно. Заметное вращение осталось
  у станций (оборот за ~80 секунд), и именно оно нужно для стыковки.

## Управление

| Клавиша | Действие |
|---|---|
| `W` / `S` | тангаж: нос вниз / вверх |
| `A` / `D` | рыскание влево / вправо |
| `Q` / `E` | крен влево / вправо |
| `↑` / `↓`, `←` / `→` | тангаж и крен (классическая схема Elite) |
| `Shift` / `Ctrl` | тяга больше / меньше; долгий `Ctrl` — задний ход |
| `X` / `Z` | тяга в ноль / полная |
| `R` / `F` | подъёмные движки: вверх / вниз (работают всегда) |
| `Tab` | выбрать цель, на которую наведён нос |
| `J` | **прыжок к выбранному**: в своей системе квантовый привод, к другой звезде — варп. Повторное нажатие отменяет |
| `B` | то же, что `J`, для квантового привода (прежняя привычка) |
| `Space` (зажать) | форсаж: втрое быстрее, пока есть заряд |
| `C` | докинг-компьютер (ближе 120 км до станции) |
| `G` | шасси: выпуск / уборка |
| `L` | посадочный компьютер (тела без атмосферы) |
| `I` | меню пилота: корабль, груз, задания, финансы (только в полёте) |
| в меню: `1`–`4`, `←`/`→`, ЛКМ | раздел; `I` или `Esc` — закрыть |
| `V` | кокпит ⇄ вид от 3-го лица |
| правая кнопка мыши | осмотр камерой от 3-го лица (отпустил — вернулась за спину) |
| `N` | звук: включить / выключить |
| `-` / `=` | громкость тише / громче |
| `M` / `H` / `~` | карта системы / справка / отладка |
| на карте: колесо, `W`/`S` | масштаб (вся система ⇄ окрестности станции) |
| на карте: `G` | карта галактики ⇄ карта системы |
| на карте: ЛКМ, `←`/`→` | выбрать объект; `Tab` — назначить его целью. В галактике выбор системы СРАЗУ делает её целью варпа |
| на карте: тянуть ЛКМ, `Пробел`, `X` | сдвинуть вид, подъехать к выбранному, сброс |
| `K` / `Shift+K` | телепорт к цели / смена высоты телепорта (для проверки картинки) |
| `Space` | вылет со станции, рестарт после крушения |
| на грунте: `Space` | коротко — зафиксировать корабль; удержать 3 с — взлёт |
| `Shift+N` | начать заново — дважды подряд (первое нажатие только предупреждает) |

Обычный перелёт: навести нос на цель, `Tab`, `J`. Три секунды
калибровки (нос держать), прыжок, выход в 250 км над целью со скоростью ноль
относительно неё.

**Прыжок один, приводов два, и игрока это не касается.** Раньше клавиши
были разные — `B` внутри системы, `J` между системами, — и различие это
техническое: пилот хочет «лететь к тому, что выбрал», а каким приводом,
дело корабля. Теперь `J` смотрит, что выбрано, и берёт нужный. Выбранная
на карте галактики система при этом стоит отметкой на экране **с самого
выбора**, а не появляется после первого нажатия: раньше `J` приходилось
жать вслепую, чтобы узнать, куда наводиться. Стыковка после этого — `C`. Вручную: войти в щель порта носом вперёд,
относительная скорость ниже 0.28 км/с, крен согласован с вращением станции
(зелёные огни порта — сверху). Подсказка со створом и индикаторами
«ОСЬ / КРЕН / СКОР» появляется в верхней части экрана при подлёте.

Посадка: `Tab` до луны → `B` → `L`. Посадочный компьютер убирает шасси на
спуске, выпускает его перед выравниванием, сам выбирает ровную площадку и
садится. Вручную: выпустить шасси (`G`) и снижаться на подъёмных движках
(`R`/`F`), продолжая при желании лететь вперёд — отдельного «посадочного
режима», где можно только вверх и вниз, нет. Касаться надо на шасси, брюхом
вниз: вертикально не быстрее 30 м/с, боком не быстрее 25 м/с, наклон к
площадке до 20°, уклон самой площадки тоже до 20°. Все пять условий показаны
в приборах подхода.

Скорость корабля — **вектор со своей инерцией** (`js/game/ship.js`). Тяга и
подъёмные движки задают лишь то, куда корабль хочет лететь; разница между
«хочет» и «летит» гасится с ограниченным ускорением, и поперёк носа этого
ускорения меньше (`SHIP.lateral`), чем вдоль. Отсюда всё поведение: разворот
на скорости уводит в занос — через полсекунды скорость всё ещё под 77° к носу
и сходится к нему только за несколько секунд, — торможение требует
расстояния, а от удара о грунт есть что отражать. Полной ньютоновщины при
этом нет: маневровые движки достаточно сильны, чтобы занос ощущался, но не
превращал каждый манёвр в баллистику.

Удар о поверхность больше не равен смерти. Касание вне допусков — это
**отскок**: нормальная составляющая скорости отражается с потерей энергии,
касательную ест трение, от неё же корабль получает кувырок, и на несколько
десятых секунды теряет управление (`ship.stun`) — всё это время он летит
свободно, только под тяготением. Без такой паузы отскока не видно:
стабилизация гасит его за десятую долю секунды.

Урон растёт как **квадрат скорости удара** — это энергия, и так оно и есть.
Шкала начинается ровно там, где кончается допуск на касание: сел в допуске —
цел, 50 м/с стоят 11% корпуса, 95 м/с сносят его целиком. Без шасси прощается
только касание: удар брюхом обходится вчетверо дороже, а аккуратная посадка
на корпус — в 5%. Корабль гибнет, когда корпуса не осталось, а не от самого
факта касания грунта.

**Шасси не меняет управление кораблём**: оно меняет предел скорости, и всё.
Компенсатор высоты работает всегда — он держит и вес, и саму высоту, — поэтому
с нейтральными ручками корабль висит на месте, а не проваливается. Проверено:
за двадцать секунд зависания высота уходит на 0.0 метра и с выпущенным шасси,
и с убранным, а `R`/`F` работают одинаково в обеих конфигурациях.

Тяготение при этом никуда не делось. Оно задаёт силу подъёмных движков (полный
ход втрое больше веса на любом теле), решает исход удара — и работает в полную
силу, пока корабль **оглушён**: после удара нет ни тяги, ни стабилизации, и
горизонтальный бросок идёт по чистой параболе (проверено: 100 м/с над луной
дают за 10 секунд километр вперёд и 74 метра вниз — ровно `gt²/2`).

Отрыв от грунта — тоже работа движков, а не толчок: на взлёте подъёмные
работают на полный ход около секунды. Импульсом это сделать нельзя — набранную
скорость тут же съест стабилизатор, как любой другой снос, и корабль осядет
обратно.

Вертикальный ход — **отдельный канал скорости**, и это не деталь реализации, а
условие его работоспособности. Гашение заноса (0.5 км/с²) на два порядка
сильнее подъёмных движков, поэтому набранную ими вертикальную скорость оно
видело как обычный снос и стирало в следующем же кадре: `R` и `F` не делали
ровно ничего нигде, кроме посадочной конфигурации, где вертикаль и так
считалась отдельно. Теперь, пока ручка отклонена, вертикаль из-под
стабилизатора выведена и скорость по ней копится; отпустил ход — канал снова
общий, и набранное гасится, как любой другой снос.

Отсюда же переделан профиль спуска у посадочного компьютера: гасить скорость
нечем, кроме подъёмных движков, поэтому на высоте h он не идёт быстрее
`√(2·a·h)` — с настоящим тяготением это главное ограничение всей посадки.
Считается это в два колена, потому что тормозить можно двумя разными
способами. На подходе корабль идёт носом вниз, и тормозят маршевые: запас
`SHIP.brake`, и от тела он не зависит. На спуске высоту держат подъёмные, и их
тяга привязана к местной тяжести — на лёгкой луне она мала. Поэтому до высоты выпуска шасси профиль считается по
маршевым, а к ней корабль приходит уже на той скорости, которую потянут
подъёмные; на стыке обе формулы дают одно и то же. Если считать всегда по
подъёмным, спуск с 500 км на слабой луне занимает шестнадцать минут; если
всегда по маршевым — корабль приходит к шасси на километре в секунду и
уходит под грунт. Оба варианта были, оба видны в тестах.

Задний ход включается тем же `Ctrl`: тяга падает до нуля, **задерживается на
нём** (0.45 с) — на этой защёлке корабль и останавливается, — и только при
дальнейшем удержании уходит в минус. Назад корабль идёт 180 м/с против 1200
вперёд: это маневровый режим, те же движки работают против своей геометрии.

В центре экрана два знака, и это не одно и то же. Прицел показывает, куда
смотрит нос; зелёный кружок с усами — **куда корабль летит на самом деле**
(в авиации это указатель вектора скорости, и висит он ровно на той точке, в
которую машина придёт, если ничего не менять). С инерцией они расходятся на
каждом развороте, и по расстоянию между ними сразу видно снос. Если корабль
движется назад, знак перечёркивается и показывает, откуда летим. На месте —
не рисуется вовсе.

Приборы подхода: как только корабль попадает в гравитационный захват, вокруг
прицела появляется рамка со всем, что нужно у поверхности, — скорость, высота
над рельефом, вертикальная и боковая скорость относительно грунта, дистанция
до цели, посадочные условия и шкала тяжести справа от рамки: столбик растёт
снизу вверх по мере приближения, под ним — сколько притяжения здесь и сколько
его у грунта. Она же и есть признак
захвата. Раньше то же самое лежало по четырём углам экрана: у поверхности это
не работает — между взглядами в разные углы корабль успевает уйти на десятки
метров. Середина рамки оставлена пустой, чтобы приборы не закрывали то, на
что целятся.

Тень корабля падает на грунт от солнца (`js/game/shadow.js`). Карт теней
здесь нет и не нужно: тень отбрасывает ровно один предмет и ровно на одну
поверхность, поэтому силуэт считается прямо — вершины корпуса проецируются
вдоль луча от солнца на плоскость грунта, по ним строится выпуклая оболочка,
а она НАТЯГИВАЕТСЯ НА РЕЛЬЕФ: сетка из 48 треугольников, каждый узел которой
опущен на настоящую высоту грунта под собой. Плоским многоугольником нельзя —
на кратере тень наполовину уходит под землю, наполовину висит над ней и
читается как отдельный предмет, проваливающийся сквозь грунт. Рисуется всё
это УМНОЖЕНИЕМ (`ZERO/SRC_COLOR`): под тенью от поверхности остаётся та доля
света, которая пришла не от солнца. Стоит 245 мкс на кадр — полсотни выборок
рельефа, без второго прохода рендера и без текстуры глубины; на
безатмосферном теле резкая тень к тому же уместна. Высота грунта считается
один раз на узел сетки, а не на вершину треугольника: иначе выборок вчетверо
больше, а это самая дорогая часть. У самого горизонта (солнце ниже 7°) и выше трёх
километров тень не строится: в первом случае она растягивается в
бесконечность, во втором её уже не разглядеть.

Масштаб у поверхности держится на трёх вещах. Камера от 3-го лица стоит в
105 метрах позади корабля, а не в двухстах, как раньше: корабль длиной 65
метров — единственный предмет известного размера в кадре, и когда камера
втрое дальше него, прибор показывает 32 метра высоты, а глаз читает «пара
сотен». И под кораблём рисуется кольцо на грунте радиусом 30 метров с
пунктирной нитью до корпуса и высотой цифрой: на пустой поверхности без
деревьев и домов сравнивать больше не с чем, а по кольцу сразу видно и
высоту, и куда корабль опустится; оно тоже лежит на рельефе, а не на
плоскости — перепад под ним и даёт чувство высоты. Третья — тень: по расстоянию между
кораблём и его тенью высота читается сразу.

Пока приборы подхода на экране, угловые панели ужимаются до того, чего в
центре нет: тяга, форсаж, корпус, имя цели с компасом. Одно и то же число в
двух местах хуже, чем в одном: глаз всё равно мечется между ними. Обе
проверки — и что всё легло в рамку, и что ничего не продублировалось —
в `tools/smoke.mjs`; они ломаются, если сдвинуть строку или вернуть дубль.

Начать заново — `Shift+N` дважды за три секунды. Одной клавишей это не
делается: рестарт стирает сохранение, и случайное нажатие стоило бы всей
партии. Корабль возвращается в порт родной станции, корпус цел, счётчики и
часы мира на нуле, сохранение переписывается сразу — иначе старое вернулось
бы при следующей загрузке страницы.

Телепорт (`K`) — инструмент проверки, а не игровая механика: он ставит корабль
к выбранной цели на одну из высот 2000 / 400 / 100 / 20 / 3 / 0.3 / 0.05 км
(`Shift+K` переключает), на освещённой стороне под углом к солнцу около 45° —
в скользящем свете рельеф виден лучше всего. Высота считается над рельефом, а
не над сферой. Так весь диапазон подлёта проходится за несколько нажатий,
вместо минут перелёта.

## Приборы растут вместе с экраном

Приборы рисовались в пикселях под экран 1600×900. На мониторе в 2556
точек подпись в девять пикселей превращается в сыпь, а панель, занимавшая
четверть кадра, занимает десятую его часть — и весь интерфейс читается как
мелкая техническая шелуха по углам. Поэтому масштаб теперь считается от
размера экрана:

```
hudScale = clamp(min(w / 1600, h / 900), 1, 2)
```

Берётся **меньшее** из двух отношений: на широком и низком экране расти по
ширине нельзя — панели полезли бы одна на другую по высоте. Предел сверху
нужен, чтобы на 4K приборы не съели кадр. Телефон считает свой масштаб по
прежнему правилу, в другую сторону: на 393 точках высоты панель в 112
пикселей занимала треть кадра.

Подобрать его на глаз можно прямо в адресной строке: `?hud=1.4`. Ручка
нужна не для красоты — насколько приборы крупны на ЧУЖОМ мониторе, из
кода не видно никак.

### Одно место на один предмет

Главная беда была не в кегле, а в том, что приборов девять и половина
показывает одно и то же дважды. На подходе к планете углы экрана
УЖИМАЛИСЬ, а их содержимое переезжало в центр: ход оказывался то слева
внизу, то посреди экрана, дистанция — то справа внизу, то в середине.
Глазу негде было закрепиться.

Теперь так:

```
слева сверху    связь и сообщения
центр           ТОЛЬКО прицел, отметка вектора и метки целей
слева снизу     КОЛОНКА: всё о корабле и о том, где он, — высота,
                вертикальная и боковая скорость, тяжесть, условия
                касания, ход, тяга, форсаж, корпус, щит, шасси
снизу по центру сканер
справа снизу    КАРТОЧКА ЦЕЛИ: вид, имя, дистанция, срок, компас, J
```

**Середина кадра свободна, и это не вкусовщина.** В виде от третьего лица
низ середины занимает САМ КОРАБЛЬ: приборы, поставленные туда, ложатся
прямо на корпус. Свободны углы и левый край.

Высота, вертикальная скорость и тяжесть живут в колонке слева, а не
отдельным прибором в центре, по второй причине: это сведения О НАС, а не
о цели и не о прицеливании. Им место рядом с ходом и корпусом, а не там,
куда смотрят, — иначе глаз обязан прыгать между двумя приборами об одном
и том же.

Колонка **растёт вверх** по мере снижения: за две тысячи километров
вертикальная скорость относительно грунта не значит ничего, ближе
полусотни километров она становится главным числом, а у самой земли к ней
добавляются условия касания. Панели при этом не переезжают: низ колонки
прибит к нижнему краю кадра.

Помощник стыковки включался за тридцать километров и висел пустой рамкой
с красными «ОСЬ/КРЕН» добрую минуту полёта — читалось это как поломка.
Теперь шесть километров: с них створ порта виден глазом.

### Облик: ни одной рамки

Рамка вокруг каждой группы съедала место и добавляла шума, не добавляя
сведений. Вместо неё колонка очерчена **одной вертикальной чертой** слева
и волосяными разделителями, а карточка цели — скобкой в углу.

Шкалы стали **отрезками, а не сплошной заливкой**. Сплошная полоса — это
индикатор загрузки из браузера: чтобы понять по ней «сколько осталось»,
глаз должен измерить длину. Десять отрезков считаются мгновенно и боковым
зрением, потому что их можно пересчитать, а не измерить. Ровно поэтому
так сделаны приборы в кабинах: топливо, заряд, ресурс.

### Что поменялось в самих приборах (вид от третьего лица)

- **Ход** — вдвое крупнее всего остального: на него смотрят в манёвре, не
  отрывая глаз от кадра. Раньше он стоял тем же кеглем, что и подписи.
- **Цель названа видом**: «ЦЕЛЬ · СТАНЦИЯ», «ЦЕЛЬ · ПИЛОТ». Имя «Lave II»
  само по себе не говорит, во что целишься — в планету, в порт или в чужой
  корабль, — а от этого зависит всё дальнейшее.
- **Дистанция словами**: «12.4 км», «лёту 48 с» вместо `ДИСТ` и `ETA`.
  Сокращение читается, только если уже знаешь, что это.
- **Подсказка клавишей прямо в панели**: «J — ПРЫЖОК К ЦЕЛИ», а при
  выбранной системе — «J — ВАРП В VESOAR». До этого «как лететь к цели»
  было написано только в справке, которую в полёте не открывают.
- Панели больше **не переезжают и не ужимаются** при подходе к планете
  настолько, чтобы их приходилось искать заново.

Кабина (мониторы на доске, `js/ui/panels.js`) пока не тронута: там свой
софт со своей вёрсткой, и мешать одно с другим в одной правке — верный
способ сломать оба.

### Проверка видит вёрстку, а не только текст

Мок холста в `tools/smoke.mjs` теперь следит за преобразованием
(translate/scale/rotate), и записанные координаты надписей — **экранные**.
Без этого угловые панели были невидимы для проверки: они рисуются в своих
пикселях, и «вылезла ли панель за кадр» спросить было нечем — а после
того как приборы стали расти, это ровно тот вопрос, который надо задавать.

Отдельный шаг ставит экран 2556×1305 с масштабом 1.45 и требует, чтобы
ни одна надпись не вышла за кадр, ни одна не осталась мельче 13 пикселей
и панель тяги не наехала на сканер.

## Кабина

Вид от первого лица — не рамка поверх кадра, а настоящая геометрия
([js/models/cockpit.js](js/models/cockpit.js)): рама фонаря, приборная
доска с тремя бухтами, два табло на стойках и штурвал. Рисуется она
отдельным проходом ([js/gl/scene.js](js/gl/scene.js), `drawCockpit`), и
на то две причины, обе про расстояние: кабина в метре от глаза, а
ближняя плоскость сцены стоит на четырёх метрах — в общем проходе от неё
не осталось бы ни грани; и она ближе всего в кадре, значит должна
закрывать собой всё. Поэтому буфер глубины очищается, проекция берётся
своя (ближняя плоскость — пять сантиметров), и нарисованное раньше
честно остаётся позади.

**Почему собрана, а не скачана.** Сначала была готовая модель с
OpenGameArt — и не подошла по существу. Любая отдельная кабина сделана
как самостоятельный корабль: со своим носом, своей крышей и своим
СТЕКЛОМ. У автора стекло прозрачное, а в этом движке прозрачности нет
вовсе (плоское затенение, цвет на грань), и кабина выходила наглухо
заваренной коробкой: неба в кадре оставалось 36%, вокруг прицела было
закрыто 39%. Вырезать проём нечем — у модели нет разделения на раму и
стекло, есть большие плиты, и вырез съедал раму вместе с ними. Оставалась
чёрная столешница. У собранной кабины проём не вырезан, а **задан**:
рамы там просто нет.

**Размеры — от поля зрения, а не на глаз.** По горизонтали видно ±50°,
по вертикали ±34°. Отсюда всё и следует:

| что | где | почему |
|---|---|---|
| стойки фонаря | ±36° вбок | в кадре по краям, прицел свободен |
| верх проёма | +29° | верхняя балка видна, но не давит |
| бухты приборов | 24° вниз | взгляд опускается, не теряя курса |
| табло на стойках | 27° вверх, ±33° | в поле зрения, но не перед прицелом |
| верх штурвала | 22° вниз | иначе руки за нижней кромкой кадра |

Последняя строка — не мелочь. Руки на настоящем штурвале лежат градусов
на сорок ниже глаза: у человека это в поле зрения (у него оно под 120°),
а в кадре игры уже нет. Кабина, в которой не видно собственных органов
управления, теряет смысл, поэтому колонка вынесена вперёд ровно
настолько, чтобы верх штурвала попадал в кадр.

**Приборы — это софт в мониторах** ([js/ui/panels.js](js/ui/panels.js)), а
не те же угловые панели, положенные на доску. Разница существенная: от
третьего лица прибор — это надписи поверх кадра, фоном им служит сам
космос. На мониторе надписей мало — нужен корпус: подложка, заголовок,
сетка, рамка и вёрстка под свой размер. Первый заход как раз и выглядел
наклейкой на доске.

Экранов пять: слева двигатели (скорость крупно, шкалы тяги, форсажа и
корпуса), по центру круглый локатор с развёрткой, справа цель с
дистанцией, временем и компасом, а на стойках — связь (лента сообщений)
и системы (привод, шасси, посадочный компьютер). Сетка подложки здесь не
украшение: на ровной заливке глаз не видит ни границ экрана, ни его
наклона, а по сетке видно и то, и другое — она едет вместе с
перспективой.

Кладутся они не «примерно туда»: HUD берёт из геометрии центр бухты, обе
её оси и размер, проецирует их на экран и строит по ним преобразование
холста ([js/ui/hud.js](js/ui/hud.js), `onPanel`). Поэтому показания
лежат на доске вместе с её наклоном и перспективой, а при повороте
головы едут вместе с ней. Внутри блока перспектива считается линейной —
на куске доски в четверть метра разница меньше пикселя.

**Голова на шее.** В кабине правая кнопка мыши поворачивает взгляд, а не
облетает корабль: глаз остаётся на месте, кабина поворачивается вокруг.
Пределы другие, чем от третьего лица, — назад только через плечо (110°),
вниз до приборной доски: у шеи свои упоры. Опустив взгляд, видно всю
доску и штурвал целиком.

**Штурвал ходит за ручками.** Не за угловой скоростью корабля, а именно
за ручками (`ship.control`): штурвал держит пилот, и стоять он должен
там, куда его отклонили, даже если корабль ещё не пошёл. До упора он
доходит за 0.18 с — быстрее, чем раскручивается корпус (0.7 с), иначе
управление выглядит запаздывающим. Крен поворачивает сам штурвал на 36°,
тангаж качает колонку на 14°.

**Ось экрана берётся от направления ВЗГЛЯДА, а не от нормали.** Разница
в знаке, и стоила она зеркального текста: на табло по стойкам «СВЯЗЬ» и
«РЕЖИМ» читались задом наперёд. Правильно — так же, как строится базис
камеры (`lookAlong`: `right = cross(up, fwd)`). Проверка на это есть:
у всех пяти экранов «вправо» обязано идти вправо по кадру, «вверх» —
вверх.

**Борта — не плита.** Гладкая панель в плоском затенении даёт ровную
серую заливку на треть кадра: ребро между двумя одинаковыми
плоскостями не видно вовсе. Поэтому стойки собраны слоями (широкое
тёмное основание, светлая накладка, красная полоса по краю), по бортам
идут пояс на уровне глаз, рёбра через каждые тридцать сантиметров и
лампы, а над проёмом стоит центральный короб с накладкой.

**Свет.** Экраны — светящиеся грани (у формата граней есть флаг
`emissive`), подсветка кабины поднята до 0.55 против звёздных 0.14. Это
не произвол: при общем ambient корпус кабины уходит в ноль, и в кадре
остаются одни экраны, висящие в темноте.

На запасном пути Canvas-2D кабины нет — рисовать её там нечем. Поэтому
`game.cockpit` значит ровно «в кадре есть настоящая кабина»: приборы
тогда переезжают на доску, а стойки фонаря штрихами поверх кадра не
рисуются.

## Небо планеты

**Что было сломано.** Атмосфера рисовалась светящейся плёнкой на шаре
радиусом 1.035: яркость бралась от угла между нормалью сферы и взглядом.
У плёнки есть КРАЙ — там, где кончается меш, — и на подлёте он читался
прямой границей поперёк кадра: по одну сторону чёрный космос, по другую
сразу дневное небо. Перехода не было вовсе, потому что переходить было
нечему — плотность воздуха в картинке не участвовала.

**Что теперь.** Оболочка стала не поверхностью, а ОБЪЁМОМ: шейдер берёт
отрезок луча внутри неё и складывает вдоль него плотность по той же
барометрической формуле, по которой греется обшивка
([js/game/entry.js](js/game/entry.js), `airDensity`). Дальше всё нужное
получается само, без единого отдельного правила:

- у верха воздуха почти нет, и небо там чёрное, как в космосе, — граница
  исчезла, потому что её нет в природе;
- к горизонту луч идёт вдоль слоёв и набирает примерно `√(πR/2H)` ≈ 15
  вертикальных столбов — отсюда яркая дуга у кромки планеты;
- при снижении столб растёт по экспоненте, и небо наливается плавно;
- луч, упирающийся в грунт, обрывается на нём.

**Луч обрывается о землю ПОД КАМЕРОЙ, а не о среднюю сферу.** Рельеф
отходит от средней сферы на километры в обе стороны, и это не мелочь:

- стоя на возвышенности (в проверке под кораблём оказалось 7.2 км над
  средней сферой), луч вбок уходит до средней сферы за десятки
  километров плотного воздуха — и земля в полукилометре перед носом
  оказывается за дымкой. Замер на высоте 10 м: под углом 1° к горизонту
  9% по средней сфере против 0.8% по грунту под камерой, под 0.25° —
  100% против 3%. Это и был «туман на десяти метрах»;
- в низине (дно океана на Lave II на 12 км НИЖЕ средней сферы) корабль
  оказывается под ней, луч вниз не находит сферы вовсе — оба корня
  отрицательные — и складывает воздух через всю планету: столб в надир
  58 против 0.01. Кадр заливало молоком, хотя до земли метры.

Поэтому пол берётся из `altitudeOf` — той же функции, по которой
считаются посадка и высота в приборах, — и дополнительно опускается до
самой камеры, если та всё же оказалась ниже. Плотность при этом
по-прежнему считается от СРЕДНЕГО радиуса: сдвинь её на высоту рельефа,
и профиль уедет на километры.

Запас в этом зажиме — два метра, и именно абсолютных. Он нужен из-за
float32: у квадрата радиуса (1.8·10⁷ км²) точность около двух км², и
зажим впритык давал бы ту же заливку через раз. А доля радиуса тут
выходит боком: 10⁻⁵ от 4200 км — это 42 метра, больше самой высоты
полёта у земли, и такой зажим опускал землю ниже, чем она есть, —
туман возвращался.

### Свечение и гашение — разные числа

Небо голубое не потому, что воздух непрозрачный, а потому, что он САМ
СВЕТИТСЯ рассеянным солнцем. Настоящий воздух почти прозрачен:
вертикально он съедает пятую часть света — ночью сквозь него видны
звёзды, с орбиты видно грунт.

Связать яркость с непрозрачностью одним числом не выходит, и это
проверено на себе. Сначала так и было, и пришлось выбирать: при
толщине, достаточной для неба у грунта, планета с орбиты заливалась
молоком — с высоты 133 км гашение выходило 69% в надир и 92% под 60°, то
есть поверхности просто не было видно. Теперь чисел два:

- **гашение** `1 − e^(−τ)` — сколько света из-за воздуха до нас не
  дошло. Это физическая величина, и она маленькая;
- **свечение** `1 − e^(−τ·ATMO_GLOW)` — рассеянный солнечный свет,
  который воздух добавляет от себя. Ночью его нет вовсе: `lit` гасит
  его на теневой стороне, и ночное небо остаётся чёрным со звёздами.

`ATMO_GLOW` при этом нельзя брать большим. Честное однократное
рассеяние дало бы ровно единицу: сколько света из луча ушло, столько в
него и пришло. Двойка — надбавка за многократное рассеяние и за
отсутствие тоновой компрессии и адаптации глаза, из-за которых
настоящее небо кажется ярче своей яркости. При восьмёрке диск планеты с
двухсот километров светился в надир на 79%, и грунт пропадал под ровной
синевой — ровно то, за что зацепился глаз.

Замер на Lave II (радиус 4200 км, верх воздуха 147 км, шкала высоты
29 км):

| высота | свечение к горизонту | свечение в зенит | гашение в надир |
|---|---|---|---|
| 147 км (верх) | 0% | 0% | 18% |
| 134 км | 4% | 0.1% | 18% |
| 100 км | 17% | 1% | 18% |
| 60 км | 54% | 5% | 16% |
| 25 км | 92% | 15% | 11% |
| 0 | 100% | 33% | 0% |

Скриншот с жалобой был сделан ровно на 134 км: там небо было залито
целиком, теперь это 15% у горизонта и чистый космос над головой, а грунт
под собой виден сквозь 18% дымки.

Ручек две, обе в [js/gl/scene.js](js/gl/scene.js): `ATMO_THICK` —
оптическая толщина столба вертикально вверх от поверхности (сколько
воздух съедает), `ATMO_GLOW` — во сколько раз свечение «быстрее»
гашения. Тонкий воздух и выглядит тоньше: `body.press` умножает
толщину, то есть мир с 0.35 бар получает бледное небо той же формулой,
которой он слабее жжёт обшивку.

### Две стороны оболочки

Оболочка — объём, и вопрос в том, какая её сторона видна. Отсюда две
ветки ([js/gl/scene.js](js/gl/scene.js), `drawAir`), и это не
украшательство:

- **снаружи** видна ближняя сторона. Она лежит перед планетой, поэтому
  обычный прозрачный проход работает как надо: буфер глубины сам
  отрежет её там, где ближе оказался корабль или станция;
- **изнутри** ближняя сторона за спиной, и видна дальняя — а она лежит
  ЗА планетой. Буфер глубины выбрасывал её над всем грунтом, и при
  снижении атмосфера исчезала целиком: над головой она почти прозрачна
  по делу, а над поверхностью её просто не было. Поэтому изнутри воздух
  рисуется БЕЗ проверки глубины и раньше — сразу после поверхности, но
  до камней, станции и корабля.

Порядок при этом выходит физически верным сам собой: дымка ложится на
далёкий грунт и не ложится на то, что в двух шагах от камеры.

Ещё две особенности прохода:

- **грани отсекаются, и всегда ровно одна** — снаружи ближняя сторона
  оболочки, изнутри дальняя. Два закрашивания одного пикселя сложили бы
  столб воздуха дважды.

  Сторона и грань здесь называются «наоборот», и это не описка.
  Камерное пространство в движке ЛЕВОЕ: +z смотрит вперёд (см.
  `perspective` в [js/gl/mat4.js](js/gl/mat4.js)), и проекция зеркалит
  обход вершин. Ближняя половина сферы, обойдённая в модели против
  часовой стрелки, на экране выходит ПО часовой — то есть задней
  гранью. Значит снаружи отсекать надо `FRONT`, изнутри `BACK`.

  До сих пор это нигде не всплывало: освещение двустороннее, и
  отсечение не включалось ни в одном проходе. Ошибка стоила чёрного
  неба у самой земли — изнутри отсекалась единственная видимая сторона,
  и воздух исчезал целиком. Теперь соглашение не помнится наизусть, а
  СЧИТАЕТСЯ в проверке: она берёт настоящие матрицы, проецирует грани
  икосферы и смотрит, куда идёт обход;
- шагов интегрирования **шестнадцать**: плотность падает в 150 раз на
  отрезке, и у горизонта почти весь вклад собран у нижней точки луча. На
  восьми шагах она проскакивает между отсчётами, и по кромке идёт
  ступенчатая рябь.

Проверки на этот раздел не про «красиво», а про то, из-за чего резкая
граница вернётся:

- плотность в шейдере сверяется с `airDensity` на всех высотах;
- вертикальный столб сверяется с интегралом экспоненты, взятым на бумаге
  (0.989 против 0.993), а отношение горизонт/зенит — с `√(πR/2H)` (15.2
  против 15.0). Это проверка самого интегрирования, а не ожиданий;
- при снижении от полутора верхов до грунта самый большой шаг — 0.5% за
  0.4 км. У самой касательной картинка меняется быстрее (у края шара
  хорда набирается круто), и там проверяется другое: уменьшив шаг
  вчетверо, изменение обязано уменьшиться тоже — у разрыва оно осталось
  бы прежним;
- с верха атмосферы грунт под собой ВИДЕН (гашение 18% в надир, 35% под
  60°), а с грунта небо яркое и при этом прозрачное (свечение 79% против
  гашения 18%). Это и есть страховка от молочной планеты;
- по обе стороны верхней границы воздух рисует ровно одна ветка, и
  пустой высоты нет — включая 179 м над грунтом и высоты НИЖЕ средней
  сферы (дно океана на Lave II лежит на 12 км ниже неё);
- какая грань отсекается, проверяется счётом, а не памятью: тест
  проецирует икосферу настоящими матрицами и определяет направление
  обхода. Перепутанная сторона — это чёрное небо, и по счёту вызовов
  отрисовки её не поймать, отсечением занимается GPU;
- из низины (1.1 км над грунтом, который на 12 км ниже средней сферы)
  вид вниз такой же, как над средней сферой, а переход через её уровень
  ничем не отмечен. Без зажима сферы грунта разница там 99.7%.

## Небо системы

Фон — не чёрная пустота: по нему идёт полоса галактического диска и
висят несколько туманностей.

**Почему это фон, а не объекты в системе.** Настоящая туманность — сотни
световых лет газа; ближайшая к Солнцу в тысячи раз дальше, чем вся
планетная система поперёк. Внутри системы к ней нельзя ни подлететь, ни
даже заметить сдвиг: она рисунок на небе, который не двигается, сколько
ни лети. Поэтому туманности живут ровно там же, где звёзды, — на
бесконечности, в одном повороте камеры и без глубины. Летающие «облака
газа» между планетами выглядели бы эффектно ровно до первой попытки к
ним приблизиться.

**Всё из seed системы.** Узнаваемого здесь нет намеренно: у следующей
звезды будет свой seed, а значит другой наклон полосы, другая сторона,
где ядро, другая ширина диска, другие туманности и другие их цвета.
Меняется одно число — `SYSTEM_SEED` в [js/main.js](js/main.js), — и небо
едет за системой само.

Единственное ограничение — наклон полосы к плоскости системы от 18° до
81°. Совпади она с плоскостью орбит, глаз прочтёт её как кольцо ЭТОЙ
системы, а не как галактику вокруг; встань точно поперёк — разделит небо
ровно пополам и будет выглядеть нарисованной.

**Из чего складывается картинка** ([js/gl/nebula.js](js/gl/nebula.js)):

- **полоса диска** — колокол по широте от галактического полюса, к ядру
  ярче и толще (там балдж). Ровная полоса выглядит мазком кисти, поэтому
  по ней идут звёздные облака (шум) и тёмные волокна пыли — гребневой
  шум у самой плоскости, где пыли больше всего;
- **туманности** — до четырёх, каждая своего вида. Цвета не подобраны на
  вкус, а взяты по механизму свечения: водородная розово-красная (линия
  Hα), кислородная бирюзовая (дважды ионизованный O III), отражательная
  синяя (пыль рассеивает синее сильнее), пылевая тёплая бурая. От системы
  к системе меняется не цвет линии, а то, какие из них попались;
- туманности ставятся **в диске** (±25° от плоскости) и не ближе 35°
  друг к другу: газ собран в ту же плоскость, что и звёзды, а два
  наложившихся цветных пятна дают одно грязное;
- **холодная дымка** поверх всего: совсем чёрное небо между звёздами
  читается как дыра, а не как пространство.

**Звёзды сгущаются к той же плоскости.** Плоскость у звёзд и у полосы
обязана быть одна, иначе светящаяся полоса ляжет мимо своих же звёзд —
и это первое, что бросается в глаза. Поэтому `galaxyFor(seed)` живёт в
[js/render/starfield.js](js/render/starfield.js) и читается обоими.
Замер: в полосе ±15° лежит 50% звёзд против 26% при равномерной россыпи.
Широта в полосе — сумма трёх равномерных случайных чисел: у неё
дисперсия ровно единица, поэтому колокол нужной ширины получается
умножением на один параметр, без логарифмов и тригонометрии.

**Цена — одна выборка на пиксель.** Небо не зависит ни от времени, ни от
места, поэтому считается ОДИН раз в кубическую карту (грань 512 на
настольном профиле, 256 на телефоне), а в кадре остаётся один вызов
отрисовки и одна выборка. Считать тот же шум на каждый пиксель каждого
кадра означало бы второй по дороговизне проход после поверхности — при
том, что результат от кадра к кадру не меняется вовсе (см. «Цена
кадра»).

Печётся по ОДНОЙ грани за кадр: шесть граней по 512² — это полтора
миллиона текселей процедурного шума, примерно полкадра поверхности.
Разом это заметный рывок на старте, по грани — не видно вовсе, и к
седьмому кадру небо готово. Мипы карте не нужны: на грань приходится
90°, то есть тексель неба всегда крупнее пикселя.

В шейдере выборки подмешивается шум в полградуса яркости. Небо тёмное и
очень плавное, а текстура восьмибитная: без подмеса по градиентам пошли
бы ступеньки кольцами.

Ручки: `SKY_GAIN` (общая яркость; небо обязано остаться фоном — ярче
звёзд оно превратится в туман, на котором не видно ни звёзд, ни целей),
`SKY_BLOBS` (сколько туманностей; больше пяти небо превращается в кашу),
`Q.sky` (сторона грани). На запасном пути Canvas-2D неба нет — там
остаются только звёзды, и сгущение к диску у них то же самое.

Проверки: небо запекается ровно шесть раз за запуск и больше никогда
(пересчёт в кадре по картинке не виден вовсе — она выглядит точно так
же), стоит ровно один вызов отрисовки, у десяти разных систем нет двух
одинаковых небес, а у одного seed небо повторяется в точности.

## Телефон

Целевое устройство — iPhone 14 Pro в горизонте: **852 × 393 точки CSS
при плотности 3**. Из этих трёх чисел следует вся мобильная работа.

**Главное — площадь кадра, а не «уровень графики».** Честный кадр на
таком экране это 2556 × 1179 ≈ **3.0 мегапикселя**, больше Full HD на
шести дюймах. Игра рисует процедурную поверхность, то есть работа идёт
на каждый пиксель: плитки пекутся в текстуры, у мешей считается мелкий
рельеф, поверх ложатся пыль, камни и кабина. Поэтому плотность
ограничена двойкой — 1704 × 786 ≈ 1.3 Мп, **в 2.3 раза меньше работы**,
а разницы на шестидюймовом экране глаз не видит.

Второе по весу — **мелкий рельеф на пиксель**: он считается для каждого
закрашенного пикселя поверхности. На телефоне он выключен целиком.

Дальше урезаны бюджеты объектов ([js/core/quality.js](js/core/quality.js)):

| | настольный | мобильный |
|---|---|---|
| плиток в памяти | 440 | 200 |
| плиток в кадре (норма) | 220 | 110 |
| пикселей на тексель | 40 | 64 |
| потоков сборки | 3 | 2 |
| камней в поле | 520 | 220 |
| пылинок из-под движков | 150 | 80 |
| пылинок за бортом | 400 | 220 |
| звёзд | 950 | 600 |

Настольный профиль — ровно те числа, что были в коде до появления
профилей: на проверке стоит отдельный пункт, чтобы «оптимизация
телефона» не ухудшила игру на мониторе молча.

Профиль выбирается **один раз** при загрузке: переключать качество на
ходу значит пересобрать все плитки посреди полёта. Устройство
определяется не по строке браузера (она врёт), а по грубому указателю
(`pointer: coarse`) и наличию касаний. Проверить сенсорное управление на
настольной машине можно флагом `?touch=1`, выключить на телефоне —
`?touch=0`.

Приборы на 393 точках высоты ужимаются: панель в 112 пикселей заняла бы
треть кадра, поэтому угловые блоки масштабируются (на iPhone — 0.63).

### Сенсорное управление

Органы стоят по краям, под большими пальцами, и не лезут в середину —
там прицел ([js/ui/touch.js](js/ui/touch.js)):

* **джойстик слева** ведёт нос: вниз по экрану — нос вверх, как штурвал
  на себя; вбок — рыскание. Ход плавный, с мёртвой зоной в центре:
  палец никогда не стоит ровно в середине;
* **ползунок тяги справа** задаёт саму тягу, а не её изменение. Пальцем
  нельзя «подержать Shift»: палец либо на экране, либо нет;
* **кнопки** — форсаж (на удержании), крен, подъёмные движки, шасси,
  цель, прыжок, вид, карта, посадка;
* **палец по свободному месту** вертит камеру — тот же жест, что правая
  кнопка мыши.

Кнопки не делают ничего своего: они **нажимают те же клавиши**
(`input.tap` / `input.hold`). Поэтому выбор цели, прыжок, шасси и смена
вида работают от касаний без единой правки в игровой логике и остаются
теми же действиями, что с клавиатуры.

Вырезы экрана обходятся честно: у 14 Pro в горизонте остров съедает
полосу сбоку, снизу идёт полоса жеста «домой». Размеры отдаёт сам
браузер через `env(safe-area-inset-*)`, и проверка следит, чтобы ни один
орган под них не залез.

### Полный экран

На ПК — кнопка в правом верхнем углу (четыре уголка). На **iPhone
полноэкранного режима нет вовсе**: Safari разрешает `requestFullscreen`
только для видео, поэтому кнопка там не рисуется — она бы просто не
работала. Убрать адресную строку на телефоне можно единственным
способом: «Поделиться» → «На экран Домой»; игра объявлена как
веб-приложение (`apple-mobile-web-app-capable`) и запускается с иконки
без браузерной обвязки.

### Кеш исходников

Игра — это ES-модули, импортирующие друг друга по относительным путям.
Версию к одному тегу `<script>` добавить бесполезно: обновится точка
входа, а остальные три десятка файлов браузер возьмёт из кеша — и
страница поедет на смеси нового и старого кода. Это худший исход: не
«старая версия», а версия, которой никогда не существовало.

Поэтому кеш выключен на сервере для всех исходников сразу
([.htaccess](.htaccess)): `no-store` и без `ETag`, чтобы браузер не
обошёлся условным запросом и ответом «не изменилось». Звук и модели,
наоборот, кешируются на неделю — они не меняются, а весят на три порядка
больше кода. На перезагрузку страницы это стоит повторной загрузки
исходников; для раздачи наружу правило стоит заменить на кеширование с
версией в имени файла.

## Цена кадра

Замер на RTX 3050, окно 2549 × 1308, двести километров над луной:
**26 кадров в секунду** при 480 тысячах треугольников и 110 вызовах
отрисовки. Цифры важны именно в такой паре: и треугольников, и вызовов
тут на порядок меньше того, что карта рисует не замечая, — значит кадр
уходит не в них.

Уходит он в **заполнение**. Поверхность занимает экран целиком, а у
поверхности самый дорогой фрагментный шейдер в игре: тексель запечённой
текстуры у земли растянут на сорок пикселей (`texelTol`), и всё, что
мельче текселя, шейдер добавляет на КАЖДЫЙ пиксель — до двадцати вызовов
трёхмерного шума плюс пять масштабов кратеров по 27 ячеек решётки
каждый. Умножить на три миллиона пикселей — это и есть весь кадр.

### Что видно в отладке

Строка по `~`: `кадр 24.1 мс, карта 19.8 мс, деталь мягче ×2.4`.

Время карты берётся у таймера драйвера (`EXT_disjoint_timer_query_webgl2`,
[js/gl/gputime.js](js/gl/gputime.js)), а не выводится из fps: при
синхронизации кадров fps стоит на шестидесяти, пока запас есть, и падает
сразу вдвое, когда он кончился, — по нему не видно ни остатка запаса, ни
того, кто занят. Если «кадр» заметно больше «карты» — упирается
процессор, и смотреть надо в сборку плиток; если они близки — упирается
заполнение, и работает всё описанное ниже. Таймера может не быть (часть
драйверов его не отдаёт) — тогда в строке стоит «таймера карты нет», а
регулятор ведётся по длительности кадра.

Замер асинхронный, ответ приходит через кадр-два, поэтому запросы лежат
в очереди и читаются только готовыми: ожидание неготового остановило бы
конвейер, то есть ровно то, что измеряется. Признак `GPU_DISJOINT_EXT`
(карту отобрали) выбрасывает замер целиком.

### Регулятор детализации

Ручка цены одна — **расширение следа пикселя** (`uFwScale`,
[js/gl/detail.js](js/gl/detail.js)). Шейдер тогда считает ровно то же,
что считал бы на экране меньшего разрешения: поверхность выходит та же,
только сглаженная, как более крупный мип. Ни шва, ни скачка нормали на
стыке плиток разных уровней при этом не появляется.

Резать сам бюджет (`uMaxCs`, `uMaxOct`) **нельзя**, и это не
осторожность: частичная сумма — не менее подробная поверхность, а
смещённая. На грубой плитке вблизи нормаль уезжала на тридцать градусов,
и на стыке с подробным соседом это читалось прямой границей света и тени
поперёк грунта.

Форма регулятора та же, что у допуска плиток: нагрузка сглаживается
(0.08 за кадр), множитель ходит медленно и с мёртвой зоной — быстро
вверх (×1.03 за кадр, около 1.2 с до предела ×8) и медленно вниз (×0.99,
около 3.5 с обратно). Провал кадров надо лечить за секунду, а резкость
возвращать незаметно: иначе на пороге картинка «дышит».

Порогов два, потому что сигналы разные: по таймеру карты — 13 мс, по
длительности кадра — 20 мс. Второй обязан лежать выше 16.7 мс, иначе
регулятор срезал бы деталь на машине, которая ровно держит шестьдесят
кадров в секунду; на это стоит отдельная проверка.

Один кадр длиной в пять секунд (свернули окно) деталь почти не двигает:
выброс ограничен четырьмя нормами, поэтому резкость возвращается за
четырнадцать кадров, а не за две секунды.

**Сколько это даёт — считано, а не обещано.** В самом дорогом случае
(тексель растянут на весь допуск) окно почти во весь бюджет: 5 октав и 5
масштабов кратеров, то есть 18 вызовов шума и 135 ячеек решётки на
пиксель. След ×8 оставляет 3 октавы и 3 масштаба — 12 вызовов и 81
ячейку, **на 39% меньше работы**; цифра стоит в проверке, чтобы правка
констант детализации не обессмыслила регулятор молча. Больше он и не
может: окно упирается не в след пикселя, а в бюджет (`DETAIL_MAX_CS`,
`DETAIL_MAX_OCT`), а поднимать предел выше ×8 нельзя — там шейдер
перестаёт добавлять к запечённой текстуре что-либо заметное, и
поверхность становится такой, какой она была до подгрузки плиток.

Поэтому остаток разрыва закрывает не он, а `?scale=`: работа на кадр
падает линейно по числу пикселей, и 0.75 — это ещё −44%.

### Ночная сторона

За 148° от солнца мелкий рельеф не считается вовсе. Наклон нормали
ограничен величиной 1.6, то есть 58°, — значит дальше этого угла ни один
склон света уже не поймает, и от рельефа остаётся только подкраска
впадин и валов на поверхности, освещённой одним рассеянным светом
(ambient 0.14). Над ночной стороной это весь экран, и двадцать вызовов
шума на пиксель там уходили в никуда.

### Ручки в адресной строке

| | что делает | зачем |
|---|---|---|
| `?fw=1` | всегда полная резкость | картинка «как до регулятора», для сравнения |
| `?fw=8` | всегда самая грубая деталь | посмотреть, чем платим за кадры |
| `?scale=0.7` | сцена в 0.7 разрешения окна | слабая карта |
| `?aa=0` | без сглаживания краёв | память и полоса на слабой карте |

`?scale=` — это вдвое меньше пикселей при 0.7 и вчетверо при 0.5.
Приборы им не портятся: они рисуются на **своём** холсте в полном
разрешении, поэтому надписи остаются резкими, а мягче становится только
сцена. Ниже 0.35 параметр не опускается — там пропадают камни и стойки
шасси, то есть предметы, по которым глаз меряет высоту. Допуск плиток
тоже считается в пикселях буфера: на половинном разрешении та же плитка
даёт вдвое меньшую ошибку на экране, и дробить её дальше незачем.

Что сюда сознательно НЕ пошло: отсев задних граней (поверхность и так
отсекается по горизонту, а двустороннее освещение нужно тоннелю порта
станции) и более мелкий тексель плиток — он переносит работу из кадра в
запекание, но вчетверо увеличивает число плиток и памяти ради одной
октавы, то есть примерно четверти выигрыша.

## Выбор цели

Цели **видны на экране сразу**: у каждой планеты, луны, станции и
орбитального маркера в кадре стоит значок — кружок у тел (у них есть
размер), квадрат у станций, косой крест у маркеров (точка в пустоте, за
которую не зацепишься). Наводишь нос — значок под прицелом загорается
белым с янтарным кольцом, под приборами появляется его имя и дистанция.
`Tab` выбирает его.

Перебора списка по `Tab` больше нет. В системе два десятка целей, и
щёлкать через полсистемы до нужной — худший способ выбрать то, что и так
видно на экране.

Две вещи в правиле выбора важнее, чем кажется:

- мерой служит зазор до **края** объекта, а не угол до его центра (угол
  минус угловой радиус, и угловой радиус — через арксинус, потому что
  край шара это точка касания луча зрения). Поэтому планета во полнеба
  выбирается, пока прицел стоит на ней хоть где-нибудь, а не только
  когда наведён ровно в центр. У станций и маркеров радиус мал или
  нулевой, и мера вырождается в обычный угол;
- под прицелом нередко оказывается несколько объектов сразу — планета и
  её станция, тело и его орбитальные маркеры. Повторное нажатие
  перебирает **их**, и только их.

Допуск наведения 12° (`AIM_CONE`): заметно больше дрожания руки и
заметно меньше расстояния между соседними целями в небе. Не наведён ни
на что — выбор не меняется, а в ленте появляется «НАВЕДИ НОС НА ЦЕЛЬ».

Значки рисуются в две линии — тёмной широкой подложкой и своей поверх
неё. Без подложки метка теряется: она тонкая и той же яркости, что
звёзды и подсвеченный край планеты, а искать её глазами приходится
именно на этом фоне.

Имя наведённой цели стоит в **постоянном месте** под приборами, а не у
самого значка: значок наведённой цели по определению стоит у прицела, а
середина кадра обязана оставаться пустой — приборы не закрывают то, во
что целятся. Заодно строка не прыгает по экрану вслед за целью.

## Масса в развороте

Корабль ощущался игрушечным не потому, что вертелся быстро, а потому, что
трогался с места рывком. Угловая скорость набиралась по экспоненте, а та в
первый же миг выдаёт максимальное ускорение: на крене это было 10.7°/с в
первом же кадре.

Теперь маневровые дают **момент**, а не угловую скорость, и вращение
раскручивается и останавливается с постоянным угловым ускорением — 2.2°/с за
первый кадр, дальше ровной прямой. Задаётся при этом время, а не ускорение
(тот же приём, что у форсажа): `SHIP.rotRamp = 0.7 с` — за столько крен
выходит на предел. Остальные оси считаются из **момента инерции корпуса**,
а он — из габаритов самой модели (67 м в размахе, 65 в длину, 19 в высоту):

| | предел | разгон | останов | разворот на 180° |
|---|---|---|---|---|
| тангаж | 49°/с | 0.35 с | 0.37 с | 3.9 с |
| рыскание | 32°/с | 0.42 с | 0.43 с | 5.9 с |
| крен | 92°/с | 0.67 с | 0.70 с | 2.3 с |

Рыскание тяжелее всех ровно потому, что корпус широкий и длинный, но
плоский: момент маневровых один на все оси (проверкой закреплено), а
ускорения выходят разными сами.

**Камера больше не приклеена к корпусу.** Пока она повторяла ориентацию
корабля кадр в кадр, на развороте вращался мир, а корабль стоял в кадре
неподвижно — так выглядит модель на подставке. Теперь камера догоняет нос с
запаздыванием (0.14 с), а крен — вдвое медленнее (0.3 с): корабль успевает
повернуться **внутри** кадра. Плюс снос от ускорения — разгоняясь, корабль
уходит от камеры вперёд, — и подтягивание к корпусу у самой земли.

Из-за этого прицел переехал: он теперь рисуется там, **куда смотрит нос**, а
не в середине кадра. С запаздывающей камерой середина кадра носу больше не
равна, и рисовать прицел по центру стало враньём.

**Маневровые видно и слышно.** Сопла пыхают ровно тогда, когда приложен
момент, — на раскрутке и на остановке; держать постоянное вращение в пустоте
не стоит ничего, и там они молчат. Точки сопел ищутся по самой модели
(крайняя вершина корпуса в нужную сторону), парами на противоположных концах:
чтобы поднять нос, газ идёт из-под носа и поверх хвоста. Звук — тот же канал,
что у подъёмных движков, но тише и звонче: сопла мельче.

## Высота у поверхности

С двадцати метров над грунтом высота не читалась вовсе — глаз говорил
«километр». Причина не в разрешении рельефа (плитки доходят до метровых
ячеек), а в том, что **на метровом масштабе у рельефа ничего нет**: замер
шероховатости после вычета уклона дал 4.9 м на участке 200 м, 1.3 м на 40 м,
12 см на 10 м и 1 см на 3 м. Гладкая наклонная плоскость выглядит одинаково с
любой высоты.

Четыре вещи, которые это чинят:

- **камни известного размера** (`js/gl/rocks.js`) — россыпь от 70 см до 3 м
  вокруг корабля: камень каждые пятнадцать метров, две трети мельче полутора,
  самые крупные поднимаются над грунтом на два с половиной. Шаг решётки
  постоянный, а радиус поля растёт с высотой (80–180 м): плотность россыпи —
  свойство грунта, а не того, с какой высоты на него смотрят. Растянутый вместе
  с полем шаг давал один камень на сорок метров, то есть два-три в кадре — их
  не было видно вовсе. Это единственный источник силуэта и параллакса на
  нужном масштабе:
  шейдерная деталь только наклоняет нормаль, а более мелкая сетка рельефа
  даёт сантиметры. **Каждый камень кладёт свою тень** — вытянутый прочь от
  солнца восьмиугольник на грунте, длиной «высота камня / тангенс высоты
  солнца». Без неё камень, на который смотрят сверху, читается как пятно
  краски: сверху он всё равно многоугольник, и предметом его делает только
  тень. Тени идут тем же мешем, что и сами камни, — один вызов отрисовки на
  всё поле. Расстановка детерминированная и привязана к телу — те же
  камни на тех же местах между запусками, при переезде поля ничего не
  «переставляется». Собирается поле порциями по 40 камней, потому что на
  каждый приходится выборка рельефа;
- **кратерная лестница доведена до метра**: масштабов стало шестнадцать
  вместо двенадцати. Каждый обрыв лестницы читается как «залитый» грунт на
  своей высоте — десятый оставлял без воронок всё мельче 14 метров,
  двенадцатый — мельче четырёх;
- **пыль из-под движков** (`js/game/dust.js`) — то, по чему на посадочных
  кадрах видно, что до грунта осталось метров пять. Ниже 40 метров, летит
  баллистически в местной тяжести: на луне (1.5 м/с²) встаёт на 15.6 м, на
  каменистой планете (2.4 м/с²) — на 13.4. Берётся она от РАБОТЫ ДВИГАТЕЛЕЙ,
  а не от положения ручки, и разница тут принципиальная: корабль висит над
  грунтом без единого нажатия — а держат его подъёмные движки, потому что с
  убранным шасси компенсатор высоты в точности гасит вес. Доля этой тяги
  выводится из модели: полный ход даёт втрое больше веса, значит на зависание
  уходит треть. На выпущенном шасси компенсатора нет — и пыли под стоящим
  кораблём тоже. Маршевые метут грунт отдельно и позади корабля, куда достаёт
  их струя. Живёт всё это в осях тела, а не мира: внутри захвата корабль
  переносится вместе с поверхностью, и пыль в мировых координатах отставала
  бы на сотни метров в секунду;
- **камера у грунта подтягивается к корпусу** (до 62% выноса ниже 400 м): чем
  ближе точка съёмки к кораблю, тем вернее глаз читает высоту по его размеру.

## Тень корабля

Тень строилась как **выпуклая оболочка** проекции корпуса, и от корабля
оставался ромб: у этого корпуса настоящий силуэт занимает 56% площади своей
оболочки — узкий нос, ступенчатый корпус и широкие крылья в корме сливались в
один кусок.

Теперь на грунт кладутся те грани, которые отвёрнуты от солнца (их-то свет и
не достаёт), и тень повторяет корабль со всеми вырезами. Проекции граней
местами накладываются, а смешивание у тени умножающее — двойное перекрытие
давало бы чёрные пятна, поэтому грани пишутся в **трафарет**, а умножается по
нему накрывающая сетка: каждый пиксель гасится ровно один раз.

Высота под тенью берётся не под каждой вершиной (их тысячи, а рельеф — самая
дорогая функция в игре), а сеткой 7×7 настоящих высот, на которую вершины
садятся билинейно. Она же служит накрывающей сеткой — один расчёт на две
работы.

## Срыв прыжка

`B` на ходу срывает прыжок — и раньше это означало катастрофу: привод
выключался, а скорость оставалась на корабле. Шестьдесят тысяч километров в
секунду маршевыми (0.75 км/с²) не гасятся и за сутки, и корабль уносило из
системы навсегда.

Резко обнулять скорость тоже нельзя — это тот же телепорт, только наизнанку.
Поэтому срыв стал **отдельной фазой привода**: цели больше нет, но ход гасится
тем же темпом, что и на штатном выходе (5 секунд с полного хода, 150 тысяч
километров пути), и по дороге привод следит, чтобы не воткнуться в тело —
скорость ограничивается тем же кинематическим правилом, что и на подходе к
точке выхода. Проверено в лоб газовому гиганту: корабль встаёт, не подойдя к
поверхности ближе 248 км.

Заодно поправлено поведение камеры на выходе. Снос камеры — модель
преследователя с инерцией, и он про ТЯГУ корабля; в прыжке скорость задаёт
профиль, а на самом выходе она падает с тысяч км/с до нуля за один кадр.
Разность скоростей давала ускорение, которого не бывает, и камеру швыряло
вперёд на пол-корпуса. Теперь на рельсах привода сноса нет вовсе — включая
кадр выхода.

## Стоянка без экрана

Посадка раньше кончалась экраном поверх игры — ровно в тот момент, ради
которого она и затевалась. Теперь всё происходит в кадре:

- касание грунта **не** останавливает игру. Корабль стоит на стойках, движки
  работают, а в приборах появляется кнопка **«ГОТОВ К ПОСАДКЕ»**;
- короткое нажатие `Space` фиксирует корабль: стойки на замках, тяга в ноль,
  движки заглушены;
- взлёт — **удержание** `Space` три секунды, с полосой заполнения и отсчётом
  «держать ещё 1.8 с». Одна клавиша на два действия, и разводятся они
  временем: поднять корабль случайным нажатием нельзя, а полоса показывает,
  сколько ещё держать, — без неё удержание превращается в угадайку;
- всё, что показывал прежний экран, стоит строкой над кнопкой: тело,
  координаты стоянки, высота площадки и счёт посадок.

## Шасси касается грунта

Стойки разнесены на тридцать метров, а корабль ставился на стоянку **по высоте
центра масс**: на склоне в 18° пяты расходятся по высоте на 6.8 метра, и одна
уходила в грунт на четыре. Со стороны это выглядело именно так, как есть, —
стойки проходят сквозь землю.

Теперь и касание, и поза считаются по трём пятам:

- у каждой стойки **своя длина**, такая, чтобы все три пяты оказались на одной
  высоте (4.00 / 5.02 / 5.02 м у этого корпуса). С общей длиной корабль на
  ровной площадке стоял бы на двух стойках из трёх;
- **касание** — по нижней пяте, а не по центру масс: на склоне корабль
  встречает грунт раньше, чем это увидела бы высота центра;
- **поза на стоянке** — плоскость через три точки грунта под пятами. Корабль
  встаёт по площадке, а не по вертикали: на уклоне 18° он наклоняется на 12°;
- у стоек есть **ход** (±1.5 м). Грунт под тридцатью метрами колеи не плоский,
  и жёсткий треножник сесть всеми тремя пятами на него не может в принципе:
  корабль садится по средней из трёх точек, а разницу выбирают сами стойки —
  ровно как у настоящих посадочных опор. Остаточный зазор под пятой после
  этого нулевой.

## Галактика и варп-прыжок

Семь звёздных систем, между ними — варп-привод (`J`). Прыжок длится
20–34 секунды, и это не декоративная пауза: **под тоннелем старая система
выгружается из памяти целиком, а новая собирается**. Тоннель — не эффект
с загрузкой внутри, а наоборот: загрузка, которой дали форму.

### Почему в памяти только одна система

Одна система — это девять планет с процедурным рельефом, семь лун,
станции, кубическая карта неба, тысячи звёзд фона и, у ближнего тела,
плитки поверхности с запечёнными текстурами. Держать семь таких разом
нельзя, и дело не только в объёме: при сетевой игре систему пришлёт
сервер, и клиент обязан уметь получить её в момент прибытия, а не иметь
заранее.

Отсюда и порядок в `enterSystem` (`js/main.js`) — сначала оборвать, потом
отпустить, и только потом собирать:

1. **Оборвать ссылки.** Тела старого мира разложены по десятку мест: цель
   навигации, гравитационный захват, ближайшее тело, зона у поверхности,
   подсказка стыковки, отметки сканера, слежение и выбор на карте, порт,
   где корабль стоял в прошлый раз. Любая уцелевшая ссылка — это и утечка
   (старый мир не соберётся сборщиком целиком, порт тянет за собой всю
   цепочку `parent`), и настоящий баг: прибор показывал бы высоту над
   планетой, которой в этой системе нет.
2. **Отпустить видеопамять** (`GlScene.forgetSystem`). Здесь сборщик
   мусора бессилен в принципе: меши планет висят на телах старого мира,
   но сами БУФЕРЫ живут в драйвере, и ссылок из JS на них нет вовсе. Без
   явного `deleteBuffer` каждый прыжок оставлял бы в видеопамяти целую
   систему. Проверка меряет это числом: 26 мешей и 144 буфера за один
   переход.
3. **Собрать новую** — мир, навигацию, звёздный фон, небо.

Обратный порядок (собрать, потом выгрузить) держал бы в памяти две
системы разом — ровно то, чего быть не должно.

### Что происходит по секундам

| время | что |
|---|---|
| `J` | центровка: в кадре появляется кольцо, показывающее направление на чужую звезду |
| +4 с удержания | рывок: корабль по-настоящему уходит по оси, система проваливается за корму |
| +1.3 с | тоннель раскрыт полностью, мир под ним больше не рисуется |
| 30% пути | **смена системы**: старая выгружена, новая собрана, корабль поставлен к её звезде |
| остаток | прогрев: грубые меши всех тел собираются, пока их никто не видит |
| −2.6 с | тоннель гаснет, и из него проступает уже чужая звезда |

Смена приходится на глухой участок не случайно: проверка так и
сформулирована — момент передачи обязан лежать между полным раскрытием и
началом гашения. Сдвинь его на секунду раньше, и подмену видно.

**Корабль переставляется к звезде в момент смены, а не на выходе.** С этой
секунды его координаты снова что-то значат. Оставь перестановку на конец —
и всё, что успеет посчитаться за оставшиеся пятнадцать секунд, будет
посчитано для точки, которой нет ни в одной системе.

**В тоннеле не сохраняемся.** Между системами у корабля нет осмысленного
места, поэтому перезагрузка посреди прыжка возвращает туда, откуда
прыгали, — к последнему сейву ДО него.

### Прогрев вместо «прогрузки»

Пока тоннель непрозрачен, сцена не рисует ничего, кроме него: кадр из
четырёх вызовов против двадцати пяти обычных. Вместо отрисовки идёт
`warmSystem` — грубые меши (уровень 2) всех тел новой системы. Без него
прыжок только ПЕРЕНОСИЛ бы прогрузку на момент выхода: игрок вываливался
бы к звезде и смотрел, как из шаров проступают планеты.

### Тоннель

Тот же приём, что у квантового (волокна текут от точки схода, координата
вдоль потока — логарифм радиуса), плюс три добавки:

- **закрутка** — угол сдвигается на `log(r)` с коэффициентом 0.07, и прямая
  трубка становится чуть винтовой;
- **призма** — красный, зелёный и синий снимаются с разным сдвигом по
  потоку, и сдвиг растёт к краю кадра. Жгуты отливают по кромке, середина
  остаётся чистой. Три выборки вместо одной;
- **переход цвета** — тоннель окрашен в свет звезды, ОТКУДА летим, и к
  концу перекрашивается в свет той, КУДА. Это единственная часть эффекта,
  которая что-то сообщает: подлетая к красному карлику, последние секунды
  летишь в оранжевом и выходишь в тот же оранжевый уже снаружи.

**Корабль в тоннеле остаётся,** и рисуется он ПОСЛЕ стен: он внутри
тоннеля, а не за ним. Нарисованный поверх, аддитивный проход ложился на
корабль дымкой и темнил его до силуэта. Светит корабль сам тоннель —
источник ставится далеко ВПЕРЁД по оси прыжка, а подсветка снизу поднята
вчетверо: теней в тоннеле нет, есть свечение со всех сторон. Звезда для
этого не годится: до смены системы она осталась в покинутой, после смены
корабль стоит к ней вплотную, и выходил он то чёрным, то пересвеченным.
Мир при этом по-прежнему не рисуется — его там и нет.

**Точка схода считается каждый кадр** от оси прыжка в осях камеры, как у
квантового тоннеля. Прибитый к середине экрана тоннель при осмотре камерой
оставался на месте, двигался только корабль — и это читалось не как
«повернул голову», а как «корабль крутится внутри неподвижной трубы».

#### Три вещи, которых здесь нет, и почему

Первая версия была невыносимой — дословно «это что за эпилепсия, почему
ощущение что я провалился в торнадо». Разбирается это на три независимые
причины, и каждая лечится отдельно:

1. **Время шейдера собиралось из фазы потока** (`w.flow * 40`), а фаза
   считается по модулю единицы. Дважды в секунду, на каждом её обороте,
   время скакало назад на сорок единиц — и весь узор мгновенно подменялся
   другим. Это и было мельтешение. Теперь в шейдер идут прямо секунды
   прыжка, монотонно. Проверка ловит именно это: она гоняет настоящий
   привод и требует, чтобы `uTime` ни разу не пошло назад.
2. **Закрутка была 0.85** — полный оборот на каждый e-кратный радиус.
   Стены закручивались быстрее, чем убегали назад, и выходил смерч, а не
   коридор. Стало 0.07, в двенадцать раз слабее.
3. **Радуга по углу.** Цвет менялся по окружности через весь спектр, и
   кадр рябил всеми цветами сразу. Убрана целиком: цвет в кадре ровно
   один — звёздный, а разница между каналами остаётся только от призмы, и
   её ровно столько, чтобы кромка жгута не была серой.

Четвёртой шла **полоса через весь кадр от середины влево** — шов на луче
±π. Угол там разрывается на целый оборот, и обе стороны разрыва обязаны
дать одно и то же значение шума.

Первая попытка чинила это целыми гармониками: угол стал передаваться в
ОБОРОТАХ, а числа волокон — целыми (30, 69, 13, 30). Полоса осталась, и
JS-двойник шума показал почему: **шум по значению не периодичен по целому
сдвигу**. Целая гармоника гарантирует лишь то, что координата шума по обе
стороны разрыва отличается ровно на целое число, — но попадает она при
этом в ДРУГУЮ ячейку решётки, с другими случайными углами. Разрыв держался
на 0.60 по сырому шуму и 0.20 по волокну при размахе в единицу.

Помогло замыкание самой решётки: `vnoiseW` берёт индекс ячейки по модулю
периода (`mod(i.x, period)` и `mod(i.x + 1.0, period)`), и тогда ячейка
слева от разрыва и ячейка справа — это одна и та же ячейка. Двойник после
этого показывает 0.0. Целые гармоники при этом нужны по-прежнему: замыкать
решётку по модулю осмысленно только тогда, когда период целый.

Проверка держит обе половины: двойник считает разрыв числом, а пара
регулярных выражений привязывает его к тексту шейдера. Без второй половины
проверка оставалась зелёной и на расшитой решётке — двойник ведь сам по
себе остаётся правильным, и первый заход этой проверки в ловушку и
попал.

Все три зажаты проверками по тексту шейдера: скомпилировать GLSL в Node
нечем, но коэффициент закрутки, отсутствие радуги и целость скобок
читаются и так. Возврат любого из трёх роняет набор.

Поле зрения в варпе шире, чем в квантовом прыжке (104° против 92°): там
за стенами тоннеля ещё видна система и широкий угол ломал бы её
перспективу, а здесь за стенами нет ничего.

### Выбор системы и есть назначение цели

На карте системы выбор и цель разведены намеренно: там перебирают объекты,
чтобы прочитать про них, и назначение целью — отдельное решение. В
галактике читать нечего — состав чужой системы неизвестен до прибытия, и
единственное, зачем её выбирают, это чтобы туда лететь.

**Сломано это было ровно так:** цель ставилась только по `Tab`. Игрок
открывал галактику, видел подсвеченную систему, нажимал `J` — и получал
«цель не выбрана». На карте выбор есть, а цели нет. Теперь выделение на
карте галактики ВСЕГДА означает цель варпа, включая то, которое появляется
само при открытии вида. `Tab` оставлен рабочим, чтобы не наказывать за
привычку с карты системы.

### Отметка центровки: одна и честная

Направление на чужую звезду ничем в кадре не обозначено — там просто
звёзды, — поэтому по нажатию `J` появляется кольцо с лучами. Рядом с ним
промах в градусах: отметка говорит КУДА, число — СКОЛЬКО ещё. Без числа
«почти навёлся» и «ровно наоборот» выглядят на экране одинаково.

**Ровно наоборот и случалось.** `projectDir` для направления ЗА СПИНОЙ
возвращает зеркальную точку — она оказывается спереди. Цель позади давала
кольцо ровно в середине кадра: игрок наводился на него и держал сколько
угодно, привод честно видел промах в 174°, а отметка показывала «точно в
цель». Жалоба звучала как «навёлся, а ничего не происходит», и дважды.

Теперь точка разворачивается обратно и отодвигается к краю — отметка в
кадре по-прежнему ОДНА и всегда показывает, куда доворачивать. Ровно за
спиной направление доворота не определено вовсе (зеркальная точка
приходится в самую середину): тогда отметка ставится вверх, «разворачивайся».

Допуск расширен с 2.5° до 4°: камера из-за спины догоняет корабль с
запаздыванием, и «точно в центре» на глаз — это уже пара градусов промаха.

### Центровка, а не «mass lock»

Единственное условие прыжка — совместить нос с направлением на чужую
звезду и продержать четыре секунды. Привязки к массе рядом нет, хотя в
играх этого жанра она обычна: в этом проекте её уже убирали вместе с
круизным множителем — она протекала во все подсистемы разом (см.
«Статус»). Возвращать её ради одной кнопки незачем, прицел и так требует
развернуть корабль.

Прервать варп нельзя, и это честно: обрывать некуда. Старой системы уже
нет в памяти, а до новой ещё не долетели.

### Звёзды разные, и это видно

Класс звезды задаёт не только цвет. Светимость определяет радиус обитаемой
зоны (`hab = 620 000 · √L` км), а по нему расставляются планеты и меряются
все температуры:

| класс | | зона | система |
|---|---|---|---|
| M красный карлик | 0.15 L | 240 тыс. км | тесная, до 2 млн км, оранжевый свет |
| K оранжевый | 0.40 L | 392 тыс. км | |
| G жёлтый (родная) | 1.00 L | 620 тыс. км | эталон, по нему всё откалибровано |
| F бело-жёлтая | 2.20 L | 920 тыс. км | |
| A белая | 5.00 L | 1.39 млн км | растянутая, до предела в 5 млн км |

Классы раздаются **колодой**, а не броском с весами: при шести соседях
бросок в пятой части случаев не даёт ни одного красного карлика и в
половине — ни одной белой. Так и вышло с первого раза: шесть систем,
четыре жёлтые. А именно крайние классы и видно.

Расстояния между системами тоже распределены по лестнице, а не выпадают
случайно: случайные радиусы дали шесть соседей на 16–21 световом годе, и
любой прыжок шёл одинаково. Сейчас — от 7 до 25 световых лет, то есть от
20 до 31 секунды.

### Родная система собрана руками, остальные генератором

`HOME_LAYOUT` — рукотворный список: с него начинается игра, и в нём должно
быть ровно то, чему он учит (обжитая планета со станцией, безвоздушная цель
для первой посадки, гигант с лунами). Генератор такого не гарантирует, а
начинать в системе из четырёх газовых гигантов нельзя.

Остальные строит `planLayout`:

- **орбиты** — геометрическим рядом, как у настоящих систем (правило
  Тициуса-Боде). Случайные орбиты дают то две планеты вплотную, то пустоту
  в полсистемы. Край зажат тремя ограничителями сразу, и берётся самый
  тесный: общий потолок в 5 млн км (иначе квантовый прыжок туда занимает
  минуты — первая версия выносила край на 35 млн км и десять минут лёта),
  привязка к обитаемой зоне (у тусклой звезды система обязана быть тесной)
  и сам геометрический ряд. Внутренняя граница — не меньше пяти радиусов
  звезды: доля от обитаемой зоны у красного карлика заводила первую планету
  ВНУТРЬ светила;
- **вид планеты** — по поясу, то есть по тому, сколько ей достаётся света.
  Из пояса тянутся два варианта, и берётся тот, которого в системе пока
  меньше: одиночный бросок давал системы из девяти каменистых планет
  подряд;
- **порт** — хотя бы один обязательно, на планете ближе всех к обитаемой
  зоне. Без порта некуда сесть, негде начать заново и незачем сюда лететь.
  Больше четырёх портов не бывает: дальше они перестают различаться, а
  выбор «куда лететь» и есть смысл их существования;
- **место для посадки** — садиться можно только на безвоздушное, и если ни
  одного такого тела не вышло, внешней планете добавляется луна.

Что внутри чужой системы, на карте галактики **не показано**, и это не
забывчивость: системы в памяти нет. Обещать состав планет заранее значило
бы либо держать все системы разом, либо врать.

## Планеты родной системы

Девять планет, семь лун, четыре станции. Макет лежит списком
(`HOME_LAYOUT` в `js/game/world.js`) — руками, а не из seed. Остальные
шесть систем галактики строит генератор, см. раздел выше.

| № | вид | радиус | орбита | что на ней |
|---|---|---|---|---|
| Lave I | вулканическая | 1900 км | 340 тыс. км | садиться можно |
| Lave II | океаническая | 4200 км | 620 тыс. км | **дом**, станция, воздух |
| Lave III | пустынная | 3400 км | 1.02 млн км | станция, тонкий воздух |
| Lave IV | каменистая | 2600 км | 1.58 млн км | садиться можно |
| Lave V | ледяная | 1700 км | 1.95 млн км | малый мир за линией льда |
| Lave VI | газовый гигант | 8200 км | 2.42 млн км | кольца, станция, 2 луны |
| Lave VII | газовый гигант | 5600 км | 2.95 млн км | 3 луны |
| Lave VIII | ледяная | 3000 км | 3.60 млн км | 1 луна |
| Lave IX | каменистая | 2400 км | 4.40 млн км | дальняя станция, 1 луна |

**Номер — это место по расстоянию от звезды.** Отсюда правило: новое тело
вставляется в список на своё место по орбите, а не дописывается в конец.
Дописать проще, но тогда Lave IX оказалась бы между II и III, и номер
перестал бы что-либо значить. Проверка на это стоит в наборе: орбиты обязаны
строго расти, а имена — совпадать с порядком.

**Три новых мира — внешние, и это не случайность.** Всё, что ближе родной
планеты, сдвинуло бы её номер, а на «Lave II» завязаны и привычка, и замеры
в этом файле (дно океана на 12 км ниже средней сферы, верх воздуха 147 км).
Внешняя часть системы к тому же и была пустой: между 1.58 и 3.6 млн км
стояло одно тело.

**Пара газовых гигантов** — как Юпитер с Сатурном. Орбиты расходятся на
530 тыс. км; когда планеты сходятся, каждая видна с другой диском в
1.2–1.8°, то есть вдвое-втрое крупнее полной Луны. Расходятся они до
5.4 млн км, так что это событие, а не постоянная картина. Колец у второго
нет намеренно: два одинаково окольцованных гиганта читались бы как один и
тот же объект.

**Главная прибавка — не сами планеты, а луны.** Садиться можно только на
безвоздушное (`isLandable`), и таких тел было пять; стало десять. Пока
аэродинамического спуска нет, три луны нового гиганта — это половина всех
площадок в системе.

**Дальняя станция у Lave IX** стоит 80 секунд прыжка от дома — против
20–60 до всего остального, то есть дольше заявленных «полминуты-минуты».
Исключение сделано сознательно: пока все четыре станции равноудалены, выбор
между ними ничего не значит, а под будущую торговлю нужен рейс, ради
которого стоит собираться.

Прыжок к каждому из девяти тел и четырёх станций проверен целиком, с
замером минимального зазора по дороге: все доходят, нигде не задевают.
Времена — от 4 секунд до станции над домом до 80 к дальней.

### Год теперь из орбиты, а не из номера в списке

Период обращения считается по третьему закону Кеплера, `T = K·r^1.5`
(`KEPLER = 9`, коэффициент подобран так, чтобы у родной планеты год остался
прежним — 4.4·10⁹ с).

Раньше он брался из НОМЕРА в списке: `range(1.5e9, 4.0e9) * (1 + i * 0.6)`.
Это ломалось двумя способами, и оба видны только при добавлении планеты:

- вставь тело в середину — и у всех внешних менялся год, хотя с ними
  ничего не происходило;
- диапазоны соседей перекрывались, и порядок нарушался прямо в готовой
  системе. В прежней шестёрке Lave III (1.02 млн км) шла по орбите за
  147 лет, а Lave II (620 тыс. км) — за 153: ближняя планета отставала от
  дальней, и карточка тела честно показывала эту невозможную пару.

Масштаб намеренно раздут примерно в двести раз против настоящего: планета,
обгоняющая корабль, сделала бы стыковку невозможной (см. «Статус»). Годы
выходят от 51 до 2591.

### Сохранение пришлось обнулить

Ключ в `localStorage` сменён с `solar_trader_save_v1` на `v2`. Сохранение
хранит цель, порт и точку стоянки **идентификаторами** тел, а те раздаются
по порядку создания — новое тело в середине списка сдвигает все номера за
собой. Старый сейв открылся бы без единой ошибки и посадил бы корабль не
туда: id 12 был луной, а стал газовым гигантом. Проверять каждое поле на
осмысленность дороже и всё равно ненадёжно, поэтому старый сейв просто не
находится. Цена — один перезапуск от порта.

## Карта системы

`M` — план системы на плоскости орбит: светило в центре, орбиты
окружностями, тела своими же цветами (теми, какими их видно из кабины),
станции квадратами, орбитальные маркеры ромбами. Зелёный крест — корабль,
пунктир от него — к выбранному объекту.

Карта **интерактивная**, и это её смысл:

- **масштаб** — колесо мыши (вокруг курсора) или `W`/`S` (вокруг центра),
  от «вся система в кадре» до ×900. Без приближения половина системы
  недоступна в принципе: станция висит в паре тысяч километров от
  планеты, а вся система — четыре с половиной миллиона, то есть на обзорном
  масштабе станция сидит **внутри** значка своей планеты (0.6 пикселя от
  него) и ткнуть в неё нельзя;
- **выбор** — щелчок по объекту или `←`/`→` по списку системы. Стрелками
  вид сам подъезжает к выбранному и берёт масштаб так, чтобы объект был
  виден вместе со своим хозяйством: планета — с лунами и станцией,
  станция — со своей орбитой. Иначе до станции не добраться: пока она
  невидима, по ней нечем щёлкнуть;
- **цель** — `Tab`. То же действие, что и `Tab` в полёте, только целиться
  носом не надо: на карте видно всё сразу, в том числе то, что сейчас за
  спиной или за планетой;
- сдвиг вида — тянуть левой кнопкой, `Пробел` — подъехать к выбранному,
  `X` — сброс к обзору. Слева внизу масштабная линейка круглой длины
  (1/2/5 · 10ⁿ км) — по ней видно реальное расстояние, а не «примерно».

Курсор в полёте спрятан намеренно — стрелка поверх прицела лишняя ровно
там, куда смотрят, — а на карте показан: им же и выбирают.

Проекция **линейная**, а не логарифмическая, как была раньше. Логарифм
брали, чтобы внутренние орбиты не слипались в точку, но с ним у масштаба
нет смысла: вблизи планеты её луны и станция остаются в одном пикселе при
любом приближении. Орбиты здесь отличаются всего в десять раз
(0.34–3.6 млн км), и линейная карта читается без ухищрений.

Маркеры (ОМ) показываются только у **выбранного** тела и только когда
масштаб позволяет их различить: их шесть на каждое тело, и в общем виде
они хоронят под собой всё остальное. Два маркера из шести стоят над
полюсами, а карта — проекция на плоскость орбит, поэтому они приходятся
ровно на центр своего тела: такие не рисуются вовсе (ткнуть в них там
всё равно нельзя, а планету они закрывают), и маркер в любом случае
уступает телу при выборе — обратное неверно, попасть в маркер мимо тела
ничто не мешает.

### Карточка объекта

Справа — всё, что о выбранном известно: тип, описание, радиус, масса,
плотность, тяжесть (в м/с² и в g), вторая космическая, температура,
сутки, год, расстояние от светила, радиус гравитационного захвата,
атмосфера (давление, высота, состав), возможность посадки, кольца,
станция и луны, дистанция до корабля — и состояние коридора прыжка.

Ни одно число в карточке не написано от руки. Масса считается из той же
плотности, по которой работает гравитация (`js/game/gravity.js`), тяжесть
— из массы, сутки — из периода вращения, высота атмосферы — из той же
константы, по которой считается нагрев при входе. Проверки на это и
стоят: расхождение «массы в карточке» с «тяжестью в полёте» не больше
5·10⁻¹⁶, а обещание посадки совпадает с тем, что разрешает игра.

Из модели не выводятся только справочные вещи — описание, состав
воздуха, давление у поверхности, альбедо и собственный нагрев тела
(`KIND_INFO` в `js/game/bodyinfo.js`). Это числа настоящих аналогов
(Земля, Марс, Титан, Юпитер, Ио), а не подобранные на глаз, и они
работают, а не украшают: давление входит в плотность воздуха, поэтому
пустынный мир с его 0.70 бар жжёт обшивку слабее океанического (0.45
против 0.54 на 1.2 км/с), а альбедо и собственное тепло задают
температуру.

Температура считается по настоящему закону — поток падает как квадрат
расстояния, температура как корень из него, — но шкала привязана к родной
планете (255 К равновесной + 33 К парниковых = +15 °C у поверхности).
Честная светимость здесь не годится: орбиты сжаты до 0.3–3.6 млн км
(см. «Отступления от замысла»), и формула дала бы у обитаемой планеты
полторы тысячи градусов. В остальном шкала работает как надо: от светила
наружу получается +997, +15, −31, −105, −124, −181 °C, а две луны
одного типа на разных орбитах относятся строго как корень из расстояний.

## Меню пилота

`I` в полёте открывает меню пилота: **корабль**, **груз**, **задания**,
**финансы**. Разбор ввода и вёрстка — [js/ui/menu.js](js/ui/menu.js), данные —
[js/game/player.js](js/game/player.js).

### Мир под меню не останавливается

Карта (`M`) — это режим: пока она открыта, `step()` не считает ничего.
С меню так нельзя, и не из-за удобства:

- в сети остановить мир невозможно в принципе, а меню задумано как то, что
  переживёт появление онлайна;
- смысл меню в полёте — решать НА ХОДУ: сбросить груз до досмотра,
  посмотреть срок задания посреди прыжка. Остановленный мир это обессмысливает.

Поэтому корабль летит дальше, и в подвале меню всё время висит его
скорость — это предупреждение, а не украшение. Управление при этом глохнет:
`input.enabled = false` гасит все удержания (`isDown`), а нажатия
(`pressed`) читаются всегда — ими и живёт меню. Две мелочи, которые из
этого следуют и которые легко пропустить:

- `X` и `Z` (тяга в ноль и на полную) идут через `pressed`, поэтому в
  `readControls` они проверяют `input.enabled` руками — иначе тягой можно
  было бы управлять из открытого меню;
- варп-привод уходит в прыжок сам, доцентровавшись, и может сделать это
  при открытом меню. В тоннеле клавиши не разбираются вовсе, так что меню
  закрывается принудительно — иначе закрыть его было бы нечем до прибытия.

Курсор в полёте спрятан намеренно (стрелка поверх прицела — лишний знак
ровно там, где смотрят), поэтому при открытом меню он возвращается: на
карте это прицел, в меню — обычная стрелка, и закладка под курсором
подсвечивается. Без отклика непонятно, жмётся ли тут вообще что-нибудь.

На станции `I` не делает ничего: станционная часть (рынок, доска заданий,
ремонт) будет своя, и одно меню на два места превратилось бы в набор
оговорок «здесь можно, здесь нельзя».

### Что в разделах

**Корабль.** Имя и габариты берутся ИЗ МОДЕЛИ, а не записаны словами:
`HULL_SIZE` в [js/models/ships.js](js/models/ships.js) считает габаритный
ящик по крайним вершинам — 67.1 × 19.3 × 65.0 м. Характеристики и модули —
те же константы `SHIP`, по которым летает корабль. Копия любого из этих
чисел в карточке начала бы врать в тот день, когда двигатель перенастроят.
Щиты показаны строкой «НЕ УСТАНОВЛЕНЫ»: пустая строка читается как поломка
прибора, а не как «этого у тебя нет». Бак полон и не расходуется — расхода
нет ни у одного привода, и рисовать убывающую шкалу было бы враньём.

**Груз.** Трюм меряется ТОННАМИ, объём не считается вовсе: в накладной
важен вес, и он же потом будет влиять на разгон. Один товар лежит одной
кучей, а не плодит строки.

**Задания.** Срок, награда, короткое описание. Просроченное задание из
списка не пропадает и красится в красный: игрок должен видеть, что он
провалил. Снимать его и брать штраф будет доска на станции — здесь для
этого нет ни заказчика, ни счёта.

**Финансы.** Валюта — **крона**. Раздел и есть лента операций, а баланс
хранится отдельным числом: лента подрезается на 60 записях, и считать
баланс её суммой значило бы терять деньги вместе со старыми строками.
Менять баланс можно только через `ledgerAdd` — деньги без строки в ленте
были бы деньгами из ниоткуда, и на это стоит проверка.

Груз, задания и первые кроны выданы **стартовым набором** (`seedDemo`):
взять их пока негде, и без него три раздела из четырёх были бы пусты.
Убирается одной строкой в `makePlayer`, когда появится станционная
торговля.

### Раскладка выбирается по самой длинной строке

Карточка корабля описана списком строк, а не нарисована на месте: одна и
та же карточка ложится в две колонки на мониторе и в одну на телефоне.
Хватит ли ширины на две колонки, решает не размер окна, а самая длинная
строка — подпись и значение стоят в одной строке навстречу друг другу.
На телефоне (390 px) двух колонок не выходит вовсе: «ПОСАДОЧНЫЙ КОМПЬЮТЕР
ЕСТЬ» требует 26 знаков, а в колонке их 14. В одну колонку межстрочный
интервал считается из того, сколько строк надо уместить, — иначе карточка
вылезает за нижнюю кромку.

Кегль берётся по МЕНЬШЕЙ стороне рамки. По одной высоте его считать
нельзя: телефон высокий и узкий, и закладки «3 ЗАДАНИЯ» и «4 ФИНАНСЫ»
налезали друг на друга.

Всё три беды нашла не игра в браузере, а проверка вёрстки в
`tools/smoke.mjs`: она собирает координаты каждого `fillText` вместе с
выравниванием и кеглем и требует, чтобы ни одна надпись не вылезала за
рамку меню и не пересекалась с соседней по той же строке. Гоняется она на
1600×900 и на 390×844.

Ради неё пришлось починить и сам мок: `measureText` возвращал постоянные
42 пикселя. Постоянная молча отключает ВСЯКИЙ перенос по ширине — код его
зовёт, а проверка его не видит. Теперь ширина считается по кеглю и длине
строки (Consolas моноширинный, 0.55 em на знак) — той же формулой, что и
проверка, иначе запас в проверке объявлял бы виновным честно перенесённый
абзац.

## Квантовый привод

Перелёты между телами — отдельный **режим**, а не множитель скорости
(`js/game/quantum.js`). Пока привод работает, корабль идёт по рельсам:
собственной физики у него нет, скорость задаётся профилем, столкновения не
проверяются вовсе. Проверять их и нельзя: за кадр на 60 000 км/с корабль
проходит тысячу километров, и никакая проверка касания на таком шаге не
работает. Вместо них перед стартом проверяется **коридор**.

Порядок: выбрать цель (`Tab`), навести нос с точностью 3°, нажать `B`.
Калибровка идёт три секунды, и всё это время нос надо держать: сбился —
прогресс не обнуляется, а тает (случайное касание ручки в конце калибровки
не должно означать «начать сначала»). Дальше разгон за 2 с, ход, торможение
за 5 с и выход в 250 км над поверхностью цели со скоростью **ноль
относительно неё**. У станции выход в 40 км, у точки в пустоте — в ней самой.
`B` на ходу срывает прыжок.

Ближний прыжок укорачивает себя сам: на 42 000 км корабль просто не успевает
разогнаться до потолка, и всё занимает три секунды. Отдельного правила для
ближних целей не нужно. Замеры по системе: до соседней планеты 20–40 с,
через всю систему 82 с.

Скорость прыжка — характеристика КОРАБЛЯ (`SHIP.quantumSpeed`), а не
константа привода: появятся другие корпуса, у каждого будет своя.

**Коридор.** Прямая от корабля до точки выхода не должна задевать ни одно
тело. Трасса режется на 12 кусков, внутри куска тело считается неподвижным, а
расстояние до отрезка берётся аналитически. Точками трассу проверять нельзя:
на перелёте в полтора миллиона километров даже полсотни точек стоят в
30 000 км друг от друга, и планета целиком проваливается между двумя
соседними — эта ошибка была, и проверка «с обратной стороны планеты»
проходила как разрешённая. Движение тел учитывается: орбиты аналитические,
положение на любой момент считается даром (`bodyPosAt`), а перепроверять
коридор каждый кадр незачем.

Отдельный случай — корабль уже внутри запаса тела (стоит на нём или висит
рядом). Запрещать прыжок целиком нельзя: с поверхности тогда не улететь
вовсе. Поэтому требование другое — расстояние до тела не должно уменьшаться.
Курс выше местного горизонта проходит, курс в грунт — нет.

**Орбитальные маркеры.** У каждого тела шесть точек по осям на трёх радиусах
(`world.markers`). Нужны они ровно за тем, чтобы обходить помеху: от станции
прямой коридор перекрыт своей же планетой почти всегда. Шесть, а не четыре,
потому что из любой точки поверхности хотя бы один обязан быть над
горизонтом; четырёх в одной плоскости для этого не хватает. Точки
детерминированные, а не случайные: по ним запоминают маршрут.

Сам по себе маркер бесполезен — сверху не различить, какой из шести открыт.
Поэтому привод считает обход сам (`suggestHop`): берётся точка, до которой
можно дойти сейчас и из которой цель уже открывается, она ставится целью, и
на экране появляется «ОБХОД ЧЕРЕЗ … — B ЕЩЁ РАЗ». Перелёт получается в
один-два прыжка.

**Как это выглядит.** Эффекты собраны из трёх кусков, и главный из них не
полосы, а поле зрения:

- **удар по FOV** с 68° до 92° в момент разгона, потом широкий угол держится,
  пока привод разогнан. Именно это физически продаёт скорость: глаз читает
  разгон по тому, как раздвигается картинка по краям. Полосы без него
  выглядят обоями;
- **поток частиц** мимо корабля (`WARP_VS`). Первая версия растягивала в
  полосы сам звёздный фон, и выглядело это ровно так, как и должно было:
  полосы СТОЯЛИ. Звёзды бесконечно далеко, у них есть только направление, и
  двигаться относительно корабля они не могут ни при какой скорости —
  растянуть их можно, а заставить лететь мимо нельзя. Поэтому теперь это
  отдельный поток: у каждой частицы своя сторона вокруг оси, своё удаление
  от неё и своя фаза, а летит она НА камеру — продольная координата убывает,
  и угол от оси растёт как `atan(rp/z)`, то есть в точности как у предмета,
  мимо которого пролетаешь. Отсюда вся картинка: у точки схода частицы почти
  стоят, к краю кадра разгоняются и вытягиваются в длинные полосы. Длина
  полос нигде не задана — она следствие перспективы. Фаза потока копится в
  состоянии привода (`q.warp`), а не в сцене: иначе картинка зависела бы от
  частоты кадров. Звёздный фон при этом рисуется как обычно: неподвижные
  точки — их законное поведение, неподвижные полосы — нет;
- **тоннель** — полноэкранный аддитивный проход вокруг точки схода
  (`TUNNEL_FS`). Волокна текут от неё к краям, координата вдоль потока —
  логарифм радиуса, поэтому скорость разбегания растёт к краю сама собой.
  Угловая координата кратна 2π, иначе на луче ±π виден шов.

Точка схода — не центр кадра, а проекция вектора скорости: в виде от третьего
лица камеру можно отвернуть, и тоннель обязан остаться там, куда корабль
летит на самом деле. Затемнение по краям и вспышки входа-выхода рисуются на
приборном слое: тоннель аддитивный, темнить ему нечем.

## Форсаж

`Space` на удержании: **втрое** к предельной скорости (1.2 → 3.6 км/с) и
**в три с половиной раза к тяге**, полный заряд на 10 секунд хода,
восстановление за 7.5 — вдвое быстрее расхода. Это не подарок, а замысел:
форсаж нужен на отрыв от грунта и на маневр у станции, то есть на
повторение через минуту. При симметричных пятнадцати секундах между двумя
рывками ждать приходилось дольше, чем длится сам рывок.

Форсаж обязан поднимать и то и другое. Один только предел без тяги — это не
рывок, а обещание: до тройной скорости корабль полз бы восемь секунд и
упирался в конец заряда на полпути. Поэтому задано ВРЕМЯ разгона
(`SHIP.boostRamp` = 1.5 с с обычного предела до форсажного, 2.3 с с нуля), а
множитель тяги из него выведен — поменяли предел или время, он пересчитался
сам, и обещание осталось верным.

Побочное следствие, которое стоит того: тяга форсажа (1.6 км/с²) выше порога,
на котором начинает скрипеть корпус (0.88 км/с², см. «Звук»). Обычный разгон
ниже порога и молчит, форсажный — нет: движки работают за пределом, на который
рассчитан корпус, и это ровно тот случай, ради которого скрежет и заведён. Шкала — в левой панели.
Форсаж не про перелёты (для них привод), а про то, чтобы быстрее оторваться
от поверхности и резче маневрировать у станции.

**Рывок по полю зрения** — тот же приём, что у квантового привода, в меньшем
масштабе: удар в момент включения и широкий угол, пока корабль разогнан.
68° в покое, 75° в момент рывка, 78° на набранной скорости, 80° если совпало
и то и другое (у привода — 92°). Вверх угол идёт резче, чем возвращается:
рывок — событие, возврат — послевкусие.

Расширение считается по **набранной скорости сверх обычного предела**, а не по
факту нажатия: иначе картинка раздвигалась бы раньше, чем корабль поедет, и
читалась бы как дефект, а не как разгон. Сам удар (`ship.boostPunch`) живёт в
модели корабля и гаснет за полсекунды — там же, где `punch` у привода, и по
той же причине: камера его только читает.

**Замок после опустошения.** Выжег заряд — форсаж заперт, пока клавишу не
отпустят и не накопится четверть заряда (`SHIP.boostArm`). Без замка на
зажатой клавише он трещал: заряд капал и тут же тратился, форсаж включался
через кадр, и корабль вечно шёл в полтора раза быстрее предела, не платя за
это ничем. Замка «по накоплению» мало — он даёт то же самое, только циклами.
Шкала в этом состоянии красная.

### Пылинки за бортом

Скорость в пустоте не видно ничем: звёзды бесконечно далеко (и стоять на месте
— их законное поведение), до планеты миллион километров. Корабль на полном ходу
и корабль на месте выглядят одинаково, и форсаж читается только цифрой на
приборе. Поэтому за бортом идёт поток пылинок — `js/game/flow.js` и шейдер
`MOTE_VS`.

Условность здесь ровно одна, и её стоит назвать вслух: настоящая межпланетная
пыль так редка, что мимо не пролетело бы ничего за всю партию. **Плотность
выдумана.** Дальше всё следует из движения:

* пылинки стоят на месте, а мимо идёт корабль. Поэтому копится не «фаза
  эффекта», а пройденный путь: поток сам разворачивается по вектору скорости,
  тормозит вместе с кораблём и замирает, когда тот встал;
* путь берётся от **собственной** скорости, а не от смещения в мире. В
  гравитационном захвате корабль переносится вместе с планетой и проходит по
  орбите десятки километров в секунду — считай мы по миру, над неподвижной
  точкой грунта неслась бы метель;
* черта — это **смаз** за время экспозиции (`FLOW.smear` = 80 мс): 96 м обычным
  ходом, 288 м на форсаже. Ровно втрое, потому что втрое выше предел скорости.
  Никакого отдельного «режима полос» нет.

Яркость — единственное, что здесь подача, а не физика: по-честному быстрая
пылинка размазывает тот же свет по большей длине и должна тускнеть. Она
привязана к тому, насколько корабль перевалил за обычный предел скорости, а
перевалить за него можно только форсажем: `FLOW.calm` = 0.10 на обычном ходу,
1.0 на полном форсаже — разница ровно в десять раз.

**Почему пылинки настоящие, а не проекция.** Поток прыжка (`WARP_VS`) нарисован
как направления: у его частиц нет ни расстояния, ни положения, они живут в узком
конусе вокруг курса. В прыжке этого хватает, а в обычном полёте сразу видно два
изъяна — отвернул камеру, и поток пропал (сбоку его просто нет); подлетел к
планете, и поток оказался за ней (бесконечно далёкому нечем закрыть собой
близкое). Поэтому у пылинок есть координаты и глубина: они стоят в узлах
бесконечной решётки с шагом `FLOW.box` = 2 км, ближайший образ узла берётся
через `fract(...) - 0.5`, и решётка сдвигается на пройденный путь. Рисуются они
после непрозрачного прохода, с честной глубиной, но без записи в буфер.

Цена — **один вызов отрисовки на кадр**: буфер из 400 пылинок статический, вся
траектория считается в вершинном шейдере, на процессоре остаются три числа
сдвига и вектор смаза.

## Звук

Звук устроен в два слоя, и оба нужны.

**Сэмплы** (`assets/sound`, всё CC0 — источники и таблица «файл → роль» в
[assets/sound/CREDITS.md](assets/sound/CREDITS.md)) дают материал: рокот
машины, шум сопел, вой ускорителя и настоящий металл. Скрежет обшивки
синтезом получается похожим, но узнаваемо электронным — у настоящего листа
железа спектр грязный так, как полосовыми фильтрами не подделать.

**Синтез** (`js/core/sound.js`) остаётся по двум причинам. Первая: игра
обязана звучать без единого файла — склонировали репозиторий без `assets`,
открыли, и всё работает. Вторая: сэмпл сам по себе мёртв, живым его делает
ровно то же, что и синтез — скорость воспроизведения от тяги, фильтр от
оборотов, разброс высоты у каждого скрипа. Поэтому сэмплы здесь не
«проигрываются», а управляются теми же параметрами. Что работает сейчас,
видно в отладочном оверлее (`~`): `сэмплы` или `синтез`.

Разделение такое же, как у остального кода: `js/core/sound.js` — это
железо (генераторы, фильтры, WebAudio), а `js/game/audio.js` — правила:
какой у движков ход и когда корпус скрипит. Правила считаются без всякого
звукового контекста, поэтому их видно в отладке и можно проверить в Node, а
не только ухом.

Что слышно и почему:

- **Главные движки** — гул, тон и громкость которого идут за тягой. Задний
  ход звучит ниже и грязнее: те же движки работают против своей геометрии,
  и это сказано в модели корабля — звук обязан это подтверждать, иначе на
  слух задний ход неотличим от переднего.
- **Квантовый привод** — свой голос. На калибровке он воет вполсилы и
  ровно, в прыжке гудит во весь ход по текущей скорости, вход и выход
  отмечены свистом (выход — тот же свист задом наперёд). По звуку слышно,
  что происходит, раньше, чем читается надпись. Скачок скорости на разгоне
  привода при этом НЕ идёт в нагрузку на корпус: это работа привода, а не
  перегрузка, иначе корабль скрипел бы весь прыжок. Отдельно слышна натуга главных движков,
  пока корабль ещё не набрал заданную скорость.
- **Подъёмные движки** (`R`/`F`) — шипение, вверх звонче, чем вниз.
- **Скрежет металла** — не украшение, а прибор. Размер железа задаёт
  ФИЛЬТР, а не скорость воспроизведения: скорость гуляет в пределах ±20%,
  где она читается как натяжение, а дальше начинает звучать ровно тем,
  чем является, — замедленной записью. И берётся он с дверных скрипов, а
  не с ударов по листу железа: у скрипа энергия ТЯНЕТСЯ (пик огибающей на
  середине, `sustain` 0.6), у удара она вся в атаке. Обе эти вещи стоили
  первой версии звука, которая никуда не годилась. Он звучит, когда скорость
  меняют резче, чем может один канал тяги: порог 0.88 км/с² выбран между
  `SHIP.brake` (0.75) и суммой торможения с гашением заноса (0.90), так что
  обычный полёт, включая торможение в пол, молчит, а разворот на полном
  ходу — уже слышно. Поверх этого: удар о грунт (чем сильнее, тем ниже и
  дольше), посадка брюхом, захваты порта, привод шасси и — главное —
  усталость побитого корпуса. Корабль ниже 78% скрипит сам по себе, и тем
  чаще, чем меньше его осталось: это единственный прибор, который слышно,
  не глядя на панель. На стоянке металл остывает и щёлкает.

Подобрать звук ухом, не летая, можно на странице
[tools/audition.html](tools/audition.html) (открывается с того же сервера,
что и игра): она гоняет события полёта — удар, посадку брюхом, крушение,
стыковку — через тот же код, что и игра, и позволяет на лету сравнить
варианты скрипа, включая запасные из `assets/sound/alt`. Понравился
запасной — переименовать поверх основного, код трогать не нужно.

Звуковой контекст поднимается только по жесту пользователя (иначе браузер
создаст его в состоянии suspended и промолчит весь полёт), а файлы качаются
сразу при загрузке страницы — сеть жеста не требует.

## Вход в атмосферу

Влететь в воздух на скорости — значит загореться. Ударная волна рисуется
вокруг корабля оболочкой (`js/gl/shaders.js`, программа `plume`), а
считает её [js/game/entry.js](js/game/entry.js) — отдельно от рендера и
без единого обращения к GL, поэтому нагрев проверяется в Node, а не «на
глаз в браузере».

Физики ровно столько, чтобы поведение было предсказуемым:

- плотность падает по экспоненте с высотой, верх атмосферы взят там же,
  где её рисует сцена (1.035 радиуса) — иначе пламя начиналось бы там,
  где воздуха ещё не видно. Это не просто одинаковое число: небо считает
  ту же формулу (см. «Небо планеты»), и на проверке стоит сверка их
  значений на всех высотах;
- тепловой поток растёт как `√ρ · v³` (Саттон-Грейвз для лобовой точки).
  **Куб скорости здесь главное**: вдвое быстрее вошёл — в восемь раз
  горячее, и именно поэтому по цвету видно, насколько круто заходишь;
- скорость берётся относительно ВОЗДУХА, и это та же скорость, по
  которой проверяется посадка (`groundDrift`). Орбитальную вычитать
  нельзя: внутри захвата корабль уже переносится вместе с телом, и
  второе вычитание подожгло бы всех, кто просто висит над планетой;
- пороги (320 м/с до 1.4 км/с) стоят по обычному полёту: на полном ходу
  вход заметен, на форсаже корабль горит целиком. Квантовый привод сюда не
  приходит вовсе — в прыжке нет ни атмосферы, ни столкновений. Нижний порог
  вдобавок взят выше вращения самой быстрой планеты системы (206 м/с), иначе
  корабль, висящий над грунтом со скоростью 0.00, загорался бы от одного
  лишь ветра — так и было, пока это не поймали.

**Цвет зависит от скорости, а не от силы свечения.** Сила говорит,
сколько энергии уходит в обшивку (её задаёт плотность воздуха), а
цвет — насколько быстро идёшь: на околозвуковых вокруг корабля белый
конус уплотнения, на гиперзвуке — оранжево-красная плазма, как на
снимках возвращаемых аппаратов. Иначе густой воздух на малой скорости и
разреженный на большой выглядели бы одинаково, хотя это разные вещи.

Ось волны строится по вектору СКОРОСТИ, а не по носу: горит набегающий
поток, и ему всё равно, как повёрнут корабль — влетел боком, факел
пойдёт вдоль борта.

### Оболочка идёт по корпусу

Сначала волна была телом вращения — параболой вокруг вектора скорости.
Форма корабля в ней не участвовала вовсе, и в кадре это читалось как
оранжевый кокон, из которого торчат крылья.

Теперь оболочка строится из САМОГО КОРПУСА
([js/gl/mesh.js](js/gl/mesh.js), `shockGeometry`) — как пересечение
опорных полуплоскостей корабля, отодвинутых наружу на зазор. Замер на
«Челленджере»: корпус 67 × 19 × 65 м, оболочка 73 × 27 × 72 м, то есть
она плотно обтягивает силуэт (2.7:1 в плане против 3.5:1 у корпуса) и
содержит его целиком — минимальный зазор 3 м при заданных 3.6.

Обе отвергнутые попытки стоит держать в уме, потому что обе выглядят
разумно:

- **радиус опорной функции** (докуда корпус достаёт в этом
  направлении) — у плоского тела раздувает оболочку в шар: для диска
  радиуса R он даёт толщину R/2 там, где тела нет вовсе. Замер: +36 м по
  высоте вместо +7. Снова кокон;
- **луч из центра до самой дальней грани** — наоборот, слишком тесно:
  тонкие концы крыльев проскакивают между направлениями выборки, и 58
  вершин корпуса оказались СНАРУЖИ оболочки. Крылья опять торчат.

Пересечение полуплоскостей свободно от обоих: оно и содержит корабль, и
лежит к нему вплотную. Поверхность задаётся лучами из центра, поэтому
не может пересечь сама себя — а самопересечение при аддитивном
смешивании видно удвоенной яркостью в каждой складке.

Дальше оболочку доводит шейдер, и тоже по одному правилу —
**наветренности** `max(0, n·поток)`: где поверхность смотрит в поток,
волна отходит дальше и светится ярче; в аэродинамической тени тела
остаётся зарево; корма вытягивается в след по потоку. Отсюда само собой
следует, что в скольжении раскаляется подставленный борт, а не нос, —
отдельного правила на это нет.

Две вещи в шейдере не для красоты. Свечение считается по кромке
(френель), иначе оболочка закрыла бы собой корабль. И оно гасится вблизи
камеры: в виде из кокпита камера оказывается ВНУТРИ волны, и без
затухания её изнанка залила бы экран ровным светом вместо зарева
впереди.

Калибровку видно прямо в выводе проверок: таблица нагрева по высотам и
скоростям печатается в `npm test`.

## Корабль

Корпус игрока — готовая модель («Challenger» из CC0-пака Quaternius,
[CREDITS.md](CREDITS.md)), перегнанная в формат движка командой
`npm run ship`. Движок рисует корабли ПЛОСКИМ затенением и без текстур,
поэтому от исходника берётся геометрия и цвет на грань — усреднением
текстуры по UV-развёртке каждой грани. Для плоского затенения это не
потеря: ливрея, тёмный фонарь и оранжевые накладки остаются, а панельные
линии всё равно не пережили бы усреднение по грани.

Смена корабля (`npm run ship Striker`) меняет и физику: просвет под
днищем на шасси и на брюхе, длина стоек, точки факелов и зазор в створе
порта считаются ОТ ОБВОДОВ, а не заданы числами. Раньше там стояли числа
от процедурного клина — в том числе «полуразмер корабля 6 метров» в
проверке стыковки, хотя полуразмах клина был 26.

## Числа корабля живут в бэкенде

Ни одного числа корабля, оружия и снаряжения в игре больше нет. Предел
хода, разгон, угловые скорости, форсаж, шасси, трюм, корпус, щит, урон
пушки, дальность, конус доворота, числа квантового привода и цены — всё
лежит на сервере и приезжает при загрузке.

Раньше было наоборот: числа стояли константами в `js/game/ship.js`, а
база наполнялась их слепком (`tools/export.mjs`). То есть о своей
скорости и о своём уроне клиент СООБЩАЛ серверу. В одиночной игре это
неважно, в онлайне — неверно по самой сути: рядом летает второй пилот, и
у них обязан быть один свод правил, а не два.

```
server/data/specs.php     ИСТОЧНИК: числа и объяснения к ним
  -> база (ship_type, equipment_type)          сеялкой, при npm run api:setup
  -> игра                                      маршрутом catalog.specs
  -> server/data/specs.json                    слепок для игры без сервера
```

### Почему источник — PHP, а не JSON

Каждое число здесь стоит не просто так, и объяснение — половина его
ценности: без «почему 7.5, а не 15» через месяц любое из них подкрутят
наугад. В JSON комментариев нет. Держать объяснения отдельно от чисел
значит гарантированно их разрознить, поэтому источник — обычный
PHP-файл, а JSON рядом с ним машинный слепок.

Слепок нужен для автономного режима (`?offline=1`) и для проверок в
Node: сервера там нет, а числа нужны. Собирается он командой
`npm run specs` и пересобирается сам при `npm run api:setup`. Что он не
отстал, стерегут две проверки: в Node сравниваются времена правки, в
серверном наборе — само содержимое.

### Числа принадлежат модулям, а не корпусу

Модуль — это ПРЕДМЕТ, и числа лежат у него. Двигатель знает свою
скорость, разгон и тормоз; маневровые — угловые скорости и занос; щит —
ёмкость и восстановление; трюм — тоннаж; шасси — время выпуска. Корпусу
остаётся только его собственное: прочность, бак, радиус попадания и
поведение при ударе о грунт.

Так и должно быть, и вот почему это не вкусовщина. Если скорость
принадлежит корпусу, то «другой двигатель, который летит быстрее» завести
НЕЛЬЗЯ: он был бы ярлыком, за которым нет чисел. А если она принадлежит
двигателю — это строка в `equipment_type`, и ни одной правки в игре не
нужно:

```
engine     {"flight":{"maxSpeed":1.2,"accel":0.45,"brake":0.75,...}}   12 000 кр
engine_x   {"flight":{"maxSpeed":1.8,"accel":0.62,"brake":0.95,...}}   31 000 кр
```

У модуля два набора чисел, и разделены они не для красоты:

* **`flight`** — то, что модуль ДАЁТ КОРАБЛЮ. Эти числа подмешиваются в
  лётную модель поверх корпуса, и по ним корабль летит;
* **`spec`** — собственные настройки прибора, которые никуда не
  подмешиваются: ступени сканера, дальность докинг-компьютера,
  калибровка квантового привода.

Лётная модель корабля СОБИРАЕТСЯ: корпус, а поверх — числа всех
установленных модулей. Собирается она в трёх местах и одинаково — в игре
([js/game/loadout.js](js/game/loadout.js), `flightModel`), в ответе с
характеристиками ([server/src/Specs.php](server/src/Specs.php),
`mergeFlight`) и у серверной власти
([server/src/Loadout.php](server/src/Loadout.php)). Разойдись эти сборки,
клиент и сервер по-разному ответили бы, с какой скоростью летит один и
тот же корабль, — а в онлайне это решается не в пользу клиента.

Что стоит в гнёздах КОНКРЕТНОГО корабля, записано в `ship_equipment`, и
спрашивают об этом через `Loadout`. Поменять модуль можно прямо в этой
таблице — и замена переживёт перезапуск: доукомплектование заводским
набором (`Players::ensureStock`) заполняет только ПУСТЫЕ гнёзда, а
занятое не трогает. Иначе снятый двигатель возвращался бы обратно, в
гнезде оказывались бы два, и корабль летел бы по тому из них, у кого
больше `id`, — то есть по случайности. Вместимость гнезда берётся из
самой комплектации: сколько приборов этого гнезда помечено заводскими,
столько и помещается (компьютеров два — докинг и посадочный). Поэтому щит у двоих на одинаковых
корпусах бывает разный, а снять щит — значит остаться без него: попадание
пойдёт прямо в обшивку. Пустое гнездо не даёт ничего, и это не
недосмотр — без двигателя не летают; число, которого нет, даёт NaN на
первом же кадре, и это видно сразу, в отличие от тихой подстановки нуля.

В `ship_type` столбцами остались только `hull_max` и `fuel_t` — то, по
чему ходит SQL и что принадлежит самому корпусу. Столбцы щита и трюма
снесены (`Schema::dropped`, версия 6): держать их значило бы отвечать на
вопрос «какой у корабля щит» за все корабли сразу.

Пушки устроены так же и всегда были: числа у них свои и лежат при них;
оттуда же их берёт сервер, когда проверяет попадание (`Combat::weapon`).

### Как это выглядит в игре

Точка входа страницы теперь `js/boot.js`, а не сама игра: `main.js`
собирает корабль прямо при разборе своего модуля, и к этому моменту
числа обязаны быть на месте. Загрузчик берёт их у сервера, при неудаче —
из слепка, а если нет и его, пишет об этом на стартовом экране вместо
чёрного кадра.

`SHIP`, `WEAPONS`, `QUANTUM` и список модулей ПУСТЫ до загрузки — не
«со значениями на всякий случай». Значение по умолчанию это тихая ложь:
не доехали числа, корабль всё равно полетит, и никто не заметит, по
каким. Пустой объект даёт NaN на первом же кадре.

### Что осталось числами в коде — и почему

Не всякое число — настройка.

* **Следствия геометрии**: просветы шасси, моменты инерции, размеры
  корпуса. Считаются из самого меша, и сменить корабль — значит
  пересчитать их, а не вписать заново.
* **Параметры расчёта**: на сколько кусков режется трасса при проверке
  коридора, оболочка рельефа у генератора поверхности. Это приёмы
  вычисления, а не свойства привода.
* **Правила мира и полёта**: допуски стыковки и посадки, вход в
  атмосферу, тяготение. Это законы, по которым живёт мир, а не
  характеристики железа.
* **Картинка и звук**: камера, шейдеры, пыль, громкости. Бэкенду там
  делать нечего.

### Проверки

`tools/test.mjs` читает исходники и не даёт вписать число обратно. Правил
два, потому что имена вроде `accel` и `hold` слишком общие, чтобы
запрещать их всюду: у звука своё ускорение, у посадки своя высота
зависания.

* в файлах модели (`ship.js`, `weapons.js`, `loadout.js`, `quantum.js`)
  запрещено любое `имя: число` из лётной модели — именно туда константу
  и впишут, «чтобы не было NaN»;
* во всей игре запрещено `имя: ровно то самое число` — так ловится
  копия, снятая с бэкенда и разложенная где угодно ещё.

Сетевой набор (`tools/net.mjs`) проверяет, у КОГО взяты числа:
поддельный сервер отдаёт предел хода 2.5 км/с при 1.2 в слепке, и если
корабль летит на 1.2 — значит, до сервера он не дошёл. Серверный набор
проверяет, что правка в базе доходит до игры, и что модули не хранят
копий.

```
                      и только потом запустить игру

                      запуска (mode: с сервером или сам по себе)

```

Ключевые решения и их причины расписаны в комментариях к соответствующим
модулям — в частности, почему ориентация хранится тройкой векторов
(`js/core/basis.js`), почему планеты рисуются аналитически, а не полигонами
(`js/render/planetview.js`), почему орбитальные периоды огромны
(`js/game/world.js`), почему рядом с телом корабль переносится вместе с ним
(`js/game/gravity.js`) и почему наведение работает по угловой скорости, а не
по углу (`js/game/docking.js`).

Два решения, без которых WebGL на таких масштабах не работает, расписаны в
`js/gl/mat4.js`: координаты объектов уходят в шейдер как смещение ОТ КАМЕРЫ
(иначе float32 на орбите в миллионы километров теряет километры, и близкие
объекты дрожат), а глубина пишется логарифмически (иначе один буфер на
диапазон от 4 метров до сотен миллионов километров даёт z-fighting по всей
сцене).

Поверхность — отдельная механика (`js/gl/quadtree.js`, `tiles.js`, `bake.js`).
Тело нарезано квадродеревом на кубе, натянутом на сферу: шесть корневых плиток
покрывают его целиком, каждая дробится на четыре по мере приближения. Плитка
привязана к ТЕЛУ, а не к камере, поэтому считается ровно один раз и живёт в
кэше: при подлёте подгружаются новые уровни, при отлёте вытесняются далёкие,
но ничего не пересчитывается заново. Корневые плитки не вытесняются никогда —
это и есть «поверхность планеты целиком».

Для каждой плитки делается две вещи, обе по одному разу:

- **сетка** — порциями на CPU, по той же процедурной высоте, что использует
  физика посадки (`js/game/surface.js`), плюс «юбка» по краю, закрывающая щель
  на стыке с более грубым соседом;
- **текстура** — один проход запекания на GPU (`js/gl/bake.js`): в неё пишется
  нормаль поверхности со всеми деталями, какие может показать тексель, и тон
  (валы кратеров светлее, дно темнее). Рисование после этого — просто выборка.

Запекание заменило расчёт рельефа в фрагментном шейдере. Разница в объёме
работы: то считалось на каждый пиксель каждого кадра (два миллиона раз по
шестьдесят раз в секунду), это — один раз на тексель за всё время жизни плитки.
Мип-уровни строятся сразу: без них на скользящем угле нормали дают рябь.

У самой земли одной текстуры мало: тексель растягивается на десятки пикселей,
и грунт выходит гладким независимо от того, сколько уровней подгрузилось.
Поэтому шейдер продолжает текстуру ВНИЗ — считает на пиксель те масштабы,
которые в неё уже не влезли. Стыкуется это точно: вес масштаба в шейдере
ровно дополняет его вес в текстуре (та же smoothstep, взятая наоборот), так
что сумма «текстура + шейдер» не зависит от того, плитка какого уровня
оказалась под пикселем — ни шва, ни удвоенного рельефа на стыке уровней.
Далеко от камеры тексель мельче пикселя, вес нулевой, и весь расчёт
пропускается целиком.

Если разница между текселем и пикселем в бюджет шейдера не влезает, добавлять
«сколько успеется» нельзя: частичная сумма — это не менее подробная
поверхность, а поверхность с другим наклоном. Вместо этого расширяется след
пикселя: выходит та же поверхность, только сглаженная, как более крупный мип.

Уровень плитки выбирается по двум условиям сразу: по геометрической ошибке в
пикселях (её допуск подстраивается под число плиток в кадре — у процедурного
рельефа деталь есть на любом масштабе, и фиксированный допуск требует дробления
почти без дна) и по размеру текселя. Второе — не про резкость текстуры, а про
соседей: деталь ниже текселя считает шейдер, бюджет у него конечный, и на
плитке, чей тексель во много раз крупнее пикселя, деталь обрывается раньше.
Рядом с подробным соседом это видно швом — одна плитка зернистая, другая
гладкая, граница прямая; на скользящем свете гладкая сторона вдобавок уходит
в чёрное, потому что ловить свет микрорельефом ей нечем. Допуск на тексель
держит соседей в пределах двух уровней, и он же связан с бюджетом шейдера:
проверка требует, чтобы на самой грубой разрешённой плитке деталь доходила
ровно до пикселя. Не дотянется — деталь обрывается выше пикселя, и в момент
смены уровня недостающие кратеры появляются разом: это и есть «прогрузка» на
подлёте.

### Дробление: кого ждать и кого держать

Плитка дробится, только когда готовы все её потомки — иначе в грунте была бы
щель. Важно, КАКИЕ потомки считаются нужными: раньше требовались все четыре,
включая тех, что за горизонтом. Такой потомок в кадр не попадает, значит не
помечается нужным, значит через три секунды вытесняется из кэша — и в этот
момент разваливается всё поддерево под ним, разом на несколько уровней, хотя
мелкие плитки целы и лежат рядом. Потом он собирается заново, и поддерево
возвращается. Со стороны это выглядит ровно так, как и выглядело: на доли
секунды подробный рельеф подменяется грубым и тут же возвращается.

Замер на прогоне «полёт у земли, 900 кадров, 60 размеченных точек грунта»:
было **179 подмен с возвратом, худшая на 16 уровней**; стало **ноль, худшее
изменение — один уровень** (и то в одну сторону: участок уходит за спину и
честно грубеет). Чинится это тремя вещами:

- условие «ждать потомка» совпадает с отсечением при отрисовке ТОЧНО. Мягче —
  ждём того, кого никто не рисует и потому не держит в кэше; строже — дробим,
  не дождавшись того, кто рисуется, и получаем дырку;
- дробление держится с запасом (`HYST`): раз раздробив плитку, её не
  схлопывают обратно, пока ошибка не упадёт заметно ниже допуска. Без запаса
  плитка на самой границе щёлкает туда-сюда от любого шевеления допуска;
- вместе с предками от вытеснения защищены СОСЕДИ по каждому узлу — от них
  зависит дробление, хотя сами они в кадре могут и не появляться.

Допуск на геометрию ведёт один медленный регулятор. Раньше их было два —
подстройка под число плиток в кадре (прыжок на 12% за кадр вверх, 3% вниз) и
множитель от заполненности кэша, — и вместе они раскачивали допуск, а вместе
с ним и уровень всех плиток, стоящих у границы. Теперь нагрузка сглаживается,
а множитель ходит медленно и почти симметрично: допуск — это ручка качества, а
не то, что должно шевелиться каждый кадр.

### Сборка в рабочих потоках

Плитка стоит 5–13 мс чистого счёта (около половины — процедурная высота, по
вершине на каждую), а в кадре на всю сборку отводилось 6 мс. То есть одна
плитка занимала кадр целиком, а то и два. Выход на детализацию у поверхности
требует трёхсот с лишним плиток — это три с половиной секунды счёта, которые
при шести миллисекундах на кадр растягиваются секунд на десять, а на машине
послабее и на минуты. Именно это видно, если сесть у земли или перезагрузить
игру на малой высоте: рельеф ещё долго «доезжает».

Считать быстрее нельзя, а считать НЕ В КАДРЕ — можно. Геометрия плитки
(`js/gl/tilegeo.js`) не трогает ни GL, ни DOM: на входе `{kind, name, id}` тела
и адрес плитки, на выходе типизированные массивы, которые переносятся между
потоками без копирования. Поэтому она уехала в пул потоков
(`js/gl/tilepool.js`, `js/gl/tileworker.js`) — на один меньше, чем ядер, но не
больше трёх. В кадре осталась только загрузка в буферы и запекание, не больше
шести плиток за раз.

Замер в проверках: выход на детализацию с холодного кэша — **365 кадров через
кадровый бюджет против 134 через пул**, и это без учёта главного: счёт ушёл с
главного потока целиком, то есть исчезли и рывки кадра во время подгрузки.
Если `Worker` недоступен, пул молча выключается и всё считается по-старому,
порциями в кадре; что работает сейчас, видно в отладочном оверлее (`~`) —
`потоков N` или `СЧЁТ В КАДРЕ`.

Детализация рельефа — **явный параметр** (`terrain.detailForCell`): для каждой
сетки и каждой текстуры считается ровно столько октав шума и масштабов
кратеров, сколько она способна показать. Более мелкие детали не просто
бесполезны — они дают алиасинг, из-за которого поверхность выглядит «кашей».
Амплитуда нормируется по бесконечной сумме октав, чтобы добавление
детализации не меняло крупный рельеф.

Кратеры — главное, что отличает поверхность луны от «каши» из шума, и их
правдоподобие держится на четырёх вещах, каждая из которых проверяется тестом:
радиусы на одном масштабе решётки различаются в разы (одинаковые дают
«пузырчатую плёнку»), у каждого кратера своя сохранность (свежие глубокие,
старые заплывшие), плотность модулируется низкочастотной маской — «моря»
темнее и глаже, «материки» насыщены кратерами, — и эта маска действует
только на крупные масштабы. Последнее важно на посадке: мелкие кратеры
выбиты уже после заливки лавой, они есть и в морях. Посадочный компьютер
ищет ровную площадку, то есть как раз море, и без этой оговорки грунт под
кораблём выглядел бы залитым бетоном.

Нижнюю границу масштабов задаёт не фантазия, а float32: координата решётки —
это направление (по модулю 1), делённое на масштаб, и мельче ~5e-6 радиана
решётка начинает проступать ступеньками. На луне в 2400 км это метров десять;
всё, что мельче, не считается ни в шейдере, ни при запекании.

## Сервер: подготовка к онлайну

Игра пока считает всё сама и хранит сохранение в `localStorage`. Сервер
([server/](server/), PHP 8 + MySQL) — первый шаг к тому, чтобы состояние
жило не в браузере: он уже держит каталог, экономику и игроков, отвечает
по HTTP и проверяется своим набором тестов. К игре он ещё **не подключён**
(см. «Чего ещё нет» в конце раздела).

```
server/config.php        доступ к базе (localhost:3306, root) + имя базы
server/boot.php          подключение кода: ни composer, ни автозагрузчика
server/api.php           единственная дверь HTTP: api.php?r=<маршрут>
server/index.php         состояние сервера в браузере
server/src/Db.php        PDO: запросы, транзакции, UTC
server/src/Schema.php    все таблицы в одном месте
server/src/Content.php   экономика: товары, цены, чем торгует какой мир
server/data/specs.php    ЧИСЛА корабля, оружия и модулей — источник правды
server/src/Specs.php     чтение источника, выдача игре, слепок
server/src/Seeder.php    заливка каталога и содержимого (идемпотентная)
server/src/Galaxy.php    чтение каталога
server/src/Stations.php  порты: свойства, стыковка со сбором, ремонт
server/src/Auth.php      учётные записи и сессии

server/src/Ledger.php    деньги: лента операций и баланс

```

Команды:

```

npm run api:status    что сейчас в базе
npm run api:setup -- --demo    завести показательного пилота (demo/demo)

```

PHP ищется сам ([tools/php.mjs](tools/php.mjs)): в `PATH` его обычно нет,
а на второй машине XAMPP лежит по другому пути. Явно задать —
`SOLAR_PHP=C:/xampp82/php/php.exe`.

### Каталог — слепок генератора, а не вторая его копия

Сервер обязан быть хозяином каталога: в онлайне верить клиенту в том, где
стоит планета, нельзя. Но генератор уже написан и вылизан
([galaxy.js](js/game/galaxy.js), [world.js](js/game/world.js)), и
переписывание его на PHP завело бы **вторую правду** — две реализации
одного шума расходятся на третьем знаке и молча дают разные миры у
клиента и сервера.

Поэтому источник остаётся один: [tools/export.mjs](tools/export.mjs)
собирает все семь систем тем же вызовом `makeSystem`, что и игра при
прибытии, и кладёт результат в `server/data/catalog.json` (7 систем, 116
тел, 19 станций). `Seeder` заливает этот файл в базу. Рядом с каждой
системой лежит её `seed` — пока генератор общий, любой клиент соберёт ту
же систему сам, а сервер сможет это проверить.

Заливка **идемпотентна**: тела обновляются на месте по ключу «система +
локальный номер». Это не аккуратность ради аккуратности — на `body.id`
ссылаются склады станций и взятые подряды, и «снести и залить заново»
уносило бы их вместе с каталогом. Проверка на это стоит отдельная.

Локальный номер тела — тот самый `id`, который генератор раздаёт при
сборке системы и который лежит в сохранении игрока. Наружу сквозной `id`
базы не показывается вовсе.

### Что в базе

| | таблицы | откуда берётся |
|---|---|---|
| каталог | `star_system`, `body`, `station` | выгрузка генератора + [Content.php](server/src/Content.php) |
| содержимое | `ship_type`, `equipment_type`, `commodity` | константы игры + [Content.php](server/src/Content.php) |
| изменяемое | `player`, `ship`, `ship_equipment`, `cargo`, `market`, `mission`, `ledger`, `session` | сама игра |

Числа корабля и модулей приходят из тех же констант `SHIP`, по которым
корабль летает: их отдаёт [js/game/loadout.js](js/game/loadout.js) — один
список на карточку корабля в меню и на каталог сервера. Две копии этого
списка разъехались бы при первой же перенастройке двигателя, причём
молча: в игре одно число, в магазине сервера другое.

А вот цены, спрос и склады — наоборот, только на сервере. Это то, во что
играют против других игроков; посчитай их клиент, и первый же желающий
купит тысячу тонн за одну крону.

### Порт — не просто тело

Станция лежит в `body` как тело: у неё есть орбита, радиус и хозяин, как у
луны. Но всё остальное у неё своё, и живёт оно в отдельной таблице
`station`: держать сбор, уровень техники и набор услуг столбцами в `body`
значило бы завести десяток полей, пустых у ста тел из ста шестнадцати.

**Уровень техники** (1–5) считается от вида мира, вокруг которого станция
висит, плюс ступень столице системы. От него зависит, что здесь вообще
есть: на руднике у ледяной луны нет ни верфи, ни доски подрядов, и корпус
там чинят дороже. Ради этой разницы уровень и заведён — иначе все порты
одинаковы и лететь дальше незачем. В родной системе выходит от «Riveis
Station» (столица, техника 5, верфь) до рудников с техникой 1.

**Сбор за стыковку** — первый постоянный расход в игре. Без расходов
деньги только копятся, и любая награда обесценивается к третьему часу.
Берётся он один раз, при стыковке: повторный вызов `station.dock` сбор не
берёт, потому что клиент будет переспрашивать при потере связи, и это
нормальное поведение, а не попытка сжульничать.

**Ремонт за деньги** закрывает дыру, которая была в игре с самого начала:
стыковка чинила корпус даром, то есть у корпуса не было цены и разбить
его было не страшно. Теперь чинят только там, где есть чем, и по ставке,
которая ниже на развитых портах.

Честно про стыковку: сервер НЕ ЗНАЕТ, подлетел ли корабль к порту на
самом деле, — он знает только то, что прислал клиент. `station.dock`
сегодня означает «запиши, что я в порту, и возьми сбор», а не пропуск в
шлюз. Настоящей проверкой это станет вместе с физикой на сервере.

### Рынок вырастает из типов планет

Товары привязаны к видам миров, которые генератор уже расставляет: лёд
даёт воду, океан — продовольствие и технику, пустыня — минералы,
вулканический мир — редкие металлы, газовый гигант — топливо. Там, где
товар производят, он дёшев и лежит на складе; там, где его ждут, он дорог,
а склада нет — иначе туда нечего было бы везти. Отдельной «карты торговых
путей» для этого не нужно: она получается сама.

Цена считается детерминированно от пары «станция + товар» и не пляшет
между запросами: игрок обязан платить ровно то, что увидел.

### Деньги: баланс меняется только лентой

`UPDATE player SET balance` в обход [Ledger](server/src/Ledger.php)
запрещён — иначе появляются деньги ниоткуда и невозможно разобраться,
откуда. Каждая строка ленты помнит баланс ПОСЛЕ операции: лента должна
читаться как выписка из банка, в том числе после того, как старые записи
уйдут за край. На это стоят две проверки — сумма всех операций обязана
равняться балансу, и до, и после наград со штрафами.

Кроны — целые. Доли кроны в игре нет, а плавающая арифметика в деньгах
рано или поздно даёт 999.9999999.

Строка игрока в денежных операциях берётся `FOR UPDATE`. В одиночной игре
это никогда не выстрелит; в онлайне два одновременных запроса иначе
прочитают один баланс, и второй затрёт первый.

### Подряды: сделан один вид, зато целиком

Доставка проверяется без веры на слово: корабль стоит в порту назначения,
и груз лежит в трюме — и то и другое записи в базе. Груз выдаётся при
взятии подряда: иначе «доставка» превращается в «купи и довези», а это
уже торговля.

Видов «разведать тело» и «привезти образец» в выдаче нет намеренно, хотя
в схеме они предусмотрены: подтвердить их выполнение сервер сегодня не
может — для этого надо знать, где корабль был на самом деле. Выдавать
задание, выполнение которого проверяется только словом клиента, — значит
заранее согласиться, что его будут подделывать.

Срок истекает и тогда, когда игрок в игру не заходит: просроченные
подряды закрываются при первом же взгляде на список, отдельного тика у
сервера пока нет.

### Что сервер проверяет, а что нет

Проверяет **ссылки и пределы**: система есть в каталоге, порт есть и
находится в той же системе, корпус не больше заводского, тоннаж
положительный, товар торгуется здесь, денег хватает, место в трюме есть,
подряд сдают в нужном порту.

Не проверяет **само движение**: чтобы поймать «телепорт через полсистемы»
или мгновенный перелёт, нужен счёт физики на сервере, а его нет. До этого
сервер — хранилище с правилами, а не судья, и так к нему и надо
относиться.

Про защиту честно: соединение локальное и без TLS, токен идёт по сети
открытым. Для машины разработчика это ничего не меняет, но выставлять
такой сервер наружу нельзя — сначала https.

### Вызовы

Все через одну дверь, `server/api.php?r=<маршрут>`; тело — JSON или
обычная форма; токен — заголовком `X-Auth-Token`. Ответ всегда одной
формы: `{"ok":true,"data":{…}}` или
`{"ok":false,"error":{"code":"no_funds","message":"…"}}`. Код ошибки —
для игры, сообщение — для человека; разбирать сообщение нельзя.

| маршрут | вход | что делает |
|---|---|---|
| `ping` | — | жив ли сервер, версия схемы, размер каталога |
| `auth.register` / `auth.login` / `auth.logout` | — | учётная запись и токен |
| `galaxy.systems` / `galaxy.system` / `galaxy.stations` | — | каталог: галактика, система, порты системы |
| `station.info` | — | свойства порта: техника, сбор, услуги |
| `station.dock` / `station.repair` | да | встать в порт со сбором; ремонт корпуса |
| `catalog.commodities` / `catalog.ships` | — | товары, типы кораблей, модули |
| `player.state` | да | полное состояние: пилот, корабль, трюм, подряды, лента |
| `player.save` | да | сохранение полёта (то же, что уходит в localStorage) |
| `ship.impact` | да | удар о грунт: игра шлёт измерение, урон считает сервер |
| `market.prices` / `market.buy` / `market.sell` | да | рынок порта, в котором стоишь |
| `missions.board` / `.accept` / `.complete` / `.abandon` | да | доска подрядов |
| `ledger.list` | да | лента операций и итоги |

Кто требует входа — видно в одном списке ([Api.php](server/src/Api.php)), а
не в теле обработчиков: забыть проверку токена так нельзя, и на это стоит
проверка, которая проходит по всему списку маршрутов.

### Что клиент писать НЕ МОЖЕТ

Игра живёт на чужой машине: что в ней написано, решает тот, кто за ней
сидит. Поэтому граница проведена не по удобству, а по цене.

**Сервер считает всё, что чего-то стоит** — и пишет это сам:

| что | кто считает | чем |
|---|---|---|
| попадание в бою | сервер | `Combat::damage` по своим числам оружия |
| удар о грунт | сервер | `Combat::impact` по числам каталога |
| ремонт корпуса | сервер | `Stations::repair`, за деньги, только в порту |
| гибель и возвращение | сервер | `Combat::respawn` |
| щит | сервер | считается от времени последнего попадания |
| деньги, груз, подряды | сервер | `Ledger`, `Cargo`, `Missions` |

**Сохранение корпуса не пишет вовсе** — ни вверх, ни вниз. Раньше писало,
и это сводило бой к нулю: снял очередь, сохранился, корпус целый. Теперь
`player.save` принимает только то, что игра одна и знает: где корабль,
куда повёрнут, у какого тела стоит, сколько налетал.

**Удар о грунт — это событие, а не число.** Игра сообщает ИЗМЕРЕНИЕ: с
какой скоростью коснулись, стояли ли шасси, была ли поза правильной.
Во сколько это обошлось корпусу, решает сервер. Уходит измерение по
сокету, рядом с боем ([socket.js](js/net/socket.js), `reportImpact` ->
[Hub.php](server/src/Hub.php)) — соединение уже открыто, и гибель надо
тут же показать соседям; когда сокета нет, тем же занимается запрос
`ship.impact`. Считает в обоих случаях один и тот же `Combat::impact`.

Та же формула есть и в игре ([landing.js](js/game/landing.js)) — ею она
показывает удар в тот же кадр, не дожидаясь ответа, и ею живёт автономный
режим. Числа у формулы одни на обе стороны (каталог, раздел `combat`), а
что стороны считают одинаково, стережёт проверка по опорным точкам.

**Чего сервер проверить не может — и это надо знать.** Своей физики у
него нет: он не моделирует полёт. Поэтому положение корабля он
пересылает как есть, а «я коснулся грунта на 50 м/с» принимает на веру.
Подделать это можно — но выиграть этим нельзя: подделка ведёт только к
тому, что игрок разбивает СВОЙ корабль или не разбивает его. Всё, что
касается ДРУГОГО — урон, деньги, груз, — через клиента не проходит вовсе.

### Чего ещё нет

- **игра с сервером не разговаривает.** Клиент написан
  ([js/net/api.js](js/net/api.js)) и работает из консоли браузера, но
  сохранение по-прежнему идёт в `localStorage`. Перевод — отдельный шаг:
  «сохранить» перестаёт быть мгновенным и начинает иногда не получаться,
  и это надо делать с проверками, а не заодно с появлением базы;
- физики на сервере нет, а значит нет и судьи над движением;
- других игроков в кадре нет: `world.entities` под них заведён, но по
  сети никто ничего не рассылает;
- миграций схемы нет — до первого живого игрока правка схемы означает
  `npm run api:setup -- --reset`.

## Игра и сервер соединены

Игра больше не хранит себя в браузере. При запуске она спрашивает
состояние у сервера, играет с него и туда же сохраняется; `localStorage`
остался кэшем на случай, когда сервера нет.

```
login.html               страница входа (регистрации нет — см. ниже)
js/net/api.js            вызовы API поверх fetch
js/net/session.js        вход, загрузка состояния, сохранение по сети
js/net/socket.js         сокет: кто ещё летает в этой системе
server/ws/server.php     сокет-сервер на Ratchet, порт 3893
server/src/Hub.php       кто кого видит — без единого сокета внутри
server/cli/player.php    пилоты из командной строки
```

### Порядок запуска

1. Нет токена — игра **не стартует**, а уходит на `login.html`. Без входа
   сервер не отдаст ни корабля, ни денег, и показывать пустой космос
   было бы обманом.
2. Токен есть и сервер ответил — игра поднимается **с сервера**. Местный
   кэш тут же переписывается серверным состоянием: если в следующий раз
   сети не окажется, игра начнётся там, где сервер её оставил.
3. Токен есть, а сервера нет — игра поднимается из кэша, в приборах и в
   шапке меню горит «АВТОНОМНО». Выкидывать игрока из полёта из-за
   пропавшего вайфая — худшее, что можно сделать.

Отдельно есть `index.html?offline=1` — игра без сервера вовсе, на одном
браузере. Это и режим разработки, и честный ответ на «сервер не поднят».

Регистрации на странице входа нет намеренно: пока игрок один, учётную
запись проще завести командой, а открытая регистрация на машине без TLS —
это дверь, за которой некому следить.

```
php server/cli/player.php add <логин> <пароль> [имя]
php server/cli/player.php pass <логин> <новый пароль>
php server/cli/player.php list
```

### Сохранение стало сетевым, и это меняет три вещи

**Игра не ждёт сервер.** Снимок состояния ставится в очередь и уходит
фоном, не чаще раза в восемь секунд. Ждать сеть в игровом цикле нельзя —
это видно как рывок раз в несколько секунд.

**Снимок один на оба хранилища.** `savePayload()` собирает его один раз,
и он идёт и в `localStorage`, и на сервер. Два разных набора полей
означали бы, что при переезде игрок теряет половину состояния — цель
полёта, вид камеры, отмеченную систему варпа. Ради этого в таблице
`player` появились `target_body`, `warp_to`, `last_station` и `view`.

**Разбирает сохранение один код.** `applyState()` не знает, откуда
пришли данные: с сервера они сначала переводятся в тот же вид
(`serverToSave`). Иначе «загрузился из браузера» и «загрузился с сервера»
неизбежно разъедутся мелочами, и ловить это придётся руками в браузере.

При закрытии вкладки последнее сохранение уходит `sendBeacon`: обычный
`fetch` браузер на выгрузке обрывает. Заголовков beacon не умеет, поэтому
токен там идёт телом запроса — сервер принимает и так.

### Что теперь стоит денег

Стыковка проходит через сервер (`station.dock`): он берёт сбор за место и
считает стыковки. Повторный вызов сбор **не** берёт — клиент будет
переспрашивать при потере связи, и это нормальное поведение, а не
попытка сжульничать.

Бесплатный ремонт при стыковке остался только в автономной игре. С
сервером у корпуса появилась цена: на экране порта есть кнопка «РЕМОНТ ·
N кр», и чинят лишь там, где есть мастерская. Чинить даром за сам факт
стыковки значило бы обесценить и удары, и деньги разом.

### Сокет: кто ещё летает рядом

Сокет-сервер (Ratchet, порт 3893) поднимается отдельной командой:

```
npm run ws            запустить (Ctrl+C — остановить)
npm run ws:test       проверки логики присутствия, без сокетов
npm run ws:live       живая проверка: сервер, база, два клиента
npm run lan           почему с другой машины не подключается
```

Почему сокет, а не опрос по HTTP: положение чужих кораблей нужно по
нескольку раз в секунду. На опросе это десятки запросов в секунду на
каждого игрока — с полным разбором PHP и новым соединением к базе каждый
раз. Сокет держит одно соединение и шлёт один снимок на тик (пять раз в
секунду).

Вход в сокет — **тем же токеном**, что и в API: две двери с разными
правилами рано или поздно разъезжаются, и закрытой остаётся только одна.
Видно только тех, кто в **той же системе**: пилот в соседней не просто
далеко — его здесь физически нет. Второй вход тем же пилотом выбивает
первое окно, иначе игрок видит сам себя чужим кораблём.

Чужие пилоты видны тремя способами сразу, и это не излишество: корпус в
67 метров перестаёт быть различим уже за сотню километров, а знать, что
рядом кто-то есть, надо куда раньше.

- **корабль в кадре** — тем же корпусом, что и свой: других моделей пока
  нет, а пустое место там, где по приборам кто-то есть, читается как
  поломка игры;
- **квадрат с именем и расстоянием** поверх кадра — оранжевый, как
  отметки на сканере, чтобы одно читалось через другое;
- **отметка на сканере** и число рядом с ним («ПИЛОТОВ РЯДОМ 2») — в обоих
  видах, и от третьего лица, и на локаторе в кабине.

Дальность отсечения корпуса считается, а не выбирается на глаз: длина,
делённая на расстояние и умноженная на фокус камеры, — это размер в
точках экрана. Дальше одной точки рисовать меш нечего, там остаётся
метка.

### Чужое движение: пять снимков в секунду против шестидесяти кадров

Сервер шлёт положение пять раз в секунду, а кадров рисуется шестьдесят.
Показывать последнее присланное нельзя: корабль поедет пятью скачками в
секунду, и на сближении это читается не как полёт, а как подвисание сети.

Поэтому `js/game/peers.js` копит снимки, а картинку ведёт с отставанием в
четверть секунды — **между двумя** соседними снимками. Плата честная:
чужой корабль всегда там, где он был, а не где он есть. Для стрельбы так
нельзя, для «вижу, кто летит рядом» — незаметно, а рывки заметны сразу.

Опоздавший снимок не останавливает корабль: движение досчитывается по
последней известной скорости, но не дольше 0.4 с — дальше он уехал бы
туда, где его нет, и вернулся бы тем самым рывком, от которого мы
уходили. Пропали снимки совсем — через 0.8 с чужие корабли гаснут: это и
есть честный показ обрыва связи, а не корабли, висящие в космосе вечно.

По сокету идёт и **осанка** — куда смотрит нос и где у корабля верх. Без
неё развернуть чужой корабль нечем: по положению видно только путь, а
стоящий на месте смотрел бы в никуда. Сервер эти шесть чисел лишь
пересылает; нормирует их тот, кто рисует, и мусор из сети до матрицы не
доходит — один NaN гасит корабль целиком.

### Связь видна всегда, а не только когда сломалась

В левом верхнем углу постоянно висит качество связи: четыре полоски и
задержка в миллисекундах, а при потерях — их доля. Это единственный
прибор, который не про корабль, поэтому он и нарисован поверх всего, а не
на доске в кабине: сеть ломается и в варпе, и в прыжке, и на стоянке.

Причина не в любви к цифрам. Сеть редко пропадает совсем — гораздо чаще
она просто становится хуже, и в игре это выглядит как чужой корабль,
который дёргается или подвисает. Отличить «сеть подтормаживает» от «игра
тормозит» глазами невозможно, а решение — лететь ли на стыковку рядом с
чужим кораблём — принимается именно по этому.

Задержка меряется своим `ping`/`pong` по тому же сокету: время ответа
сервера — единственное, что клиент может измерить честно. Потери
считаются не по пакетам (номеров у них нет), а по **ритму**: сервер шлёт
снимок каждый тик, поэтому и дырки в потоке, и его остановка видны по
временам приходов (`js/net/quality.js`).

Считается это хитрее, чем «сколько пришло за четыре секунды»: на границе
окна такой счёт шумит на целый снимок, и чистая связь показывала пять
процентов потерь на ровном месте. Поэтому потери складываются из двух
разных вещей — дырок между пришедшими снимками и молчания с последнего.
Без второго слагаемого оборвавшийся поток выглядел бы идеальным: снимки-то
до обрыва шли ровно.

После обрыва прибор не показывает последнюю известную задержку, а пишет
«СВЯЗЬ ОБОРВАНА». Застывшая цифра врёт ровно тогда, когда на прибор и
смотрят.

### Часы мира — одни на всех

Орбиты планет, лун и станций считаются от одного числа — времени мира.
Пока игра была одиночной, оно росло у каждого своё, и это никому не
мешало. В онлайне выяснилось обратное, причём самым неприятным образом:
два пилота стояли в сотне метров друг от друга, видели друг друга
правильно, а станцию видел только один — у второго она по его времени
уехала по орбите.

Причина оказалась проще, чем выглядела: клиент подставлял в поле времени
мира **налёт пилота** (`playTimeS`). У каждого он свой — значит, и фаза
орбит своя.

Теперь время мира считает сервер (`server/src/Clock.php`), а клиент с ним
сверяется. Хранится не само время, а момент рождения мира: иначе его
пришлось бы писать в базу каждую секунду, а при остановленном сервере мир
замирал бы. Время приходит и в состоянии игрока, и **в каждом снимке**
сокета — вкладка в фоне не получает кадров, её часы отстают, и без
поправки вернувшийся к игре пилот увидел бы станцию не там, где остальные.

Подводятся часы ходом, а не рывком (`js/game/clock.js`): расхождение до
двадцати секунд выбирается ускорением или замедлением хода не больше чем
на четверть. Рывок на стыковке увёл бы станцию из-под носа. Назад часы не
идут никогда — планеты, поехавшие по орбитам вспять, это не «подвели
время», это поломка. Рывком подводится только большое расхождение: после
варпа, где мир собирается заново с нуля, и после долго спавшей вкладки.

Вся логика присутствия живёт в `Hub` и **не знает про сокеты вовсе** — он
работает с любыми объектами, умеющими `send()` и `close()`. Из-за этого её
удалось закрыть проверками без единого сетевого соединения: «пилот чужой
системы не виден», «вышедший пропал», «до входа ничего не принимается»
ломаются молча, а проверять их через настоящий сокет значит проверять
заодно порт и брандмауэр.

### Игра вдвоём по локальной сети

С другой машины игра открывается по адресу этого компьютера, а не по
`localhost`:

```
http://192.168.3.155/space_game/       (адрес свой у каждой машины)
```

Всё остальное подставится само: API берёт адрес из адресной строки
(`location.origin`), сокет — оттуда же (`location.hostname` и порт 3893).
Ни в одном файле адрес не зашит.

Мешает обычно не код, а брандмауэр Windows: Apache и сокет-сервер слушают
все сетевые платы, но входящие соединения к ним закрыты, пока не заведены
правила. Что именно не так, показывает

```
npm run lan
```

— адрес машины, слушаются ли порты 80 и 3893, пропускает ли их
брандмауэр, и готовые команды для PowerShell от имени администратора.
Правила эта команда **не заводит**: открывать порты втихую проверка не
должна.

Сокет-сервер печатает сетевой адрес при запуске — чтобы не искать его в
настройках Windows посреди игры.

### Первая зависимость в проекте

Ratchet ставится composer'ом в `server/vendor` — это первый и пока
единственный внешний код в проекте, не считая CC0-моделей и звуков.
Держать его в репозитории решено сознательно: иначе на второй машине
игра не поднимется без установленного composer, а «склонировал и
запустил» — то, ради чего здесь нет ни сборки, ни npm-зависимостей.

Ratchet 0.4 написан до PHP 8.2 и при каждом соединении ругается на
динамические свойства; в `server/ws/server.php` заглушен ровно этот класс
предупреждений, свои ошибки по-прежнему видны.

Сервер собирается **вручную**, а не через `IoServer::factory`, и это не
вкусовщина: factory заводит собственный цикл событий, и тогда таймер
рассылки, повешенный на общий цикл, не срабатывает вовсе. Сервер при этом
принимает сообщения и выглядит живым, но не шлёт ни одного снимка — и
поймала это только живая проверка, где два настоящих клиента не увидели
друг друга.

### Чего по-прежнему нет

- **сервер не судит движение.** Он принимает положение на слово: физики
  на сервере нет, и поймать «телепорт через полсистемы» нечем. То же и в
  бою: попадание докладывает стрелявший, сервер проверяет лишь то, что
  проверяемо (см. «Бой»);
- чужие корабли рисуются тем же корпусом, что и свой: пока в игре один
  тип корабля, разницы не видно, но с появлением второго её придётся
  брать с сервера;
- рынка и доски подрядов в игре нет, хотя сервер их уже отдаёт: нужны
  экраны станции;
- всё идёт открытым текстом — `http://` и `ws://`. Локально это ничего не
  меняет, но выставлять такой сервер наружу нельзя.

## Бой

Левая кнопка мыши — огонь, `Tab` — взять в цель то, на что наведён нос.
Целью может быть и чужой корабль: отдельной клавиши «прицелиться в
пилота» нет намеренно — в бою нельзя помнить, какой из двух способов
сейчас нужен.

```
js/game/weapons.js     каталог оружия, наведение, болты, попадания
js/models/ships.js     GUN_PORTS — откуда вылетают болты
js/gl/scene.js         drawBolts: болт как развёрнутый к камере четырёхугольник
server/src/Combat.php  урон, гибель, возвращение в строй
server/src/Hub.php     что сервер проверяет в попадании
```

### Оружие: вид и подвес — разные вещи

Видов три — **лазер**, **ракеты**, **турель**, — и каждый бывает
**неподвижным** или **на кардане**. Сделан пока один: лазерная пушка на
кардане. Остальные заведены в каталоге сразу, а не «когда дойдут руки»:
пустое гнездо в карточке корабля — это тоже сведение, а молчание на его
месте читается как поломка прибора.

Числа оружия лежат в бэкенде (`server/data/specs.php`) и приезжают оттуда
и в игру, и в карточку корабля, и в серверный расчёт попадания — см.
«Числа корабля живут в бэкенде». В карточке, где написано «3 урона», и в
выстреле, который снимает четыре, виноват всегда второй список; здесь его
нет.

### Четыре решения, на которых держится бой

**Болт летит, а не попадает мгновенно.** Скорость конечная — 3 км/с при
дальности 2.5 км, почти секунда полёта, — и поэтому по движущейся цели
нужно упреждение. Мгновенное попадание («луч дошёл — значит попал») убило
бы и упреждение, и уклонение разом, а вместе с ними весь бой.

**Болт уносит с собой скорость корабля.** Три километра в секунду — это
**дульная** скорость, то есть относительно стрелка; в мире к ней
прибавляется ход корабля. Пока скорость была мировой, очередь на полном
ходу отползала от носа на 3 − 1.2 = 1.8 км/с, а на форсаже (предел втрое
выше, 3.6 км/с) болты оставались за кормой и висели в воздухе: попасть
можно было, только притормозив. По той же причине упреждение считается в
осях **стрелка**, а не мира: идя с целью борт о борт одним ходом,
упреждать нечего, хотя оба мчатся. И дальность меряется от стрелка —
жизнь болта задана секундами (`range / speed`), а не остатком мировых
километров, иначе оружие теряло бы дальность тем больше, чем быстрее
летишь. Чужой болт берёт ход своего стрелка из **нашего** списка пилотов:
их скорость мы и так считаем по снимкам, а просить её у клиента значит
принимать лишнее.

**Кардан наводит сам, но в пределах конуса.** Ствол доворачивает к точке
встречи, пока та не дальше пятнадцати градусов от оси корабля; за
конусом он упирается в предел и бьёт по краю. Целиться всё равно надо —
кардан прощает промах в пятнадцать градусов, а не отменяет прицеливание.
Отметка прицела показывает, куда смотрит ствол, и зелёная она ровно
тогда, когда кардан дотянулся. Без этой отметки промах необъясним: прицел
на цели, а болты идут мимо, и причина нигде не показана.

**Попадание считает стрелявший.** У него на экране и болт, и цель в одном
времени; у жертвы чужой болт приходит с задержкой, и «попал» у двоих
получилось бы разным. Ищется попадание **отрезком**, а не точкой: на
3 км/с болт за кадр проходит полсотни метров — больше собственной длины и
больше корабля, — и проверка «попал ли центр болта в шар» пропускала бы
цель через раз.

### Что проверяет сервер

Корпус меняет только сервер, и обе стороны узнают об изменении от него.
Проверяемо и проверяется: оружие стоит на корабле, цель в той же системе,
она в пределах дальности с запасом в 1.4 (клиент считает по своему кадру,
и пакет идёт ещё полпинга — без запаса честные попадания на пределе
отбрасывались бы тем чаще, чем хуже связь), и попадания идут не чаще, чем
оружие способно стрелять.

Непроверяемо: летел ли болт на самом деле. Физики снарядов на сервере
нет, как нет и физики полёта. Это отсекает случайную ерунду и опечатки,
но не отсекает умышленный обман — сказать об этом прямо лучше, чем делать
вид, будто тут защита.

Гибель сразу превращается в состояние, из которого можно играть дальше:
корабль целый, пилот в том порту, откуда последний раз уходил. Экрана
гибели у сервера нет и быть не может — он не знает, смотрит ли кто-то в
этот момент в экран. Местный «начать заново» здесь не годится вовсе: он
завёл бы нового пилота с демо-деньгами и затёр бы им серверного.

### Щит: виден только в момент удара

Щит принимает урон вперёд корпуса и отрастает сам — в этом всё различие
между ними: корпус чинят за деньги в порту, щит ждёт несколько секунд
тишины. Поэтому и полоски у метки чужого корабля две, а не одна: по ним
за один взгляд видно, добивать или уходить.

Видно оболочку **только в момент попадания**. Постоянное свечение вокруг
корабля превратило бы бой в дискотеку, а разглядеть в нём что-либо стало
бы нельзя. Вспышка складывается из трёх вещей: еле заметной ровной
подсветки (чтобы читалась сама оболочка), яркой кромки (чтобы это была
оболочка, а не заливка поверх корабля) и пятна в точке удара.

Оболочка **повторяет форму корпуса**, а не надевает на него шар. Но не
буквально: у этого корабля высота втрое меньше размаха, и точная копия
габарита читалась бы блином, а не щитом, — поэтому оси подтянуты к
среднему на четверть (`SHIELD_AXES`).

Размер при этом подбирается **по самим вершинам**, а не по габаритному
ящику, и это не придирка: эллипсоид, который просто больше ящика, его
углов не накрывает. У корпуса со скошенными крыльями законцовки лежат
как раз в углах — и торчали из-под щита, хотя «по габаритам всё
влезало». Теперь ищется множитель, при котором внутрь попадает самая
выступающая вершина, плюс восемь процентов зазора: щит должен охватывать
корпус, а не лежать на нём. Проверка считает это по всем 935 точкам
модели. Пятно удара живёт в осях КОРАБЛЯ и
считается по параметру сферы, а не по нормали: на сплюснутой оболочке
нормаль уводит пятно тем сильнее, чем площе борт, а пятно обязано
оставаться там, куда пришёл луч, даже когда корабль развернулся.

Считает щит сервер, и считает **лениво**: никакого фонового пересчёта по
всем кораблям в базе нет, заряд выводится из времени последнего попадания
в тот момент, когда его спросили (`Combat::shieldNow`). Для оболочки,
которая только копится, этого достаточно. В игре щит тоже отрастает — но
исключительно для вида, по тем же числам из `js/game/ship.js`; настоящее
значение приходит с каждым попаданием и главнее местного.

### Болт гаснет о корпус — любой

Останавливаются о корабль ВСЕ болты, включая чужие. Чужой болт урона нам
не наносит (это решает сервер), но пролетать сквозь корпус он не должен:
именно это выглядит как «стреляют мимо, а попадают». Докладываются же
серверу только свои попадания и только по чужим кораблям, а в свой
корабль болт не попадает вовсе — он из него вылетел.

На месте удара загорается вспышка, и цвет у неё разный: холодный, когда
удар принял щит, и огненный, когда дело дошло до корпуса. Зажигается она
СРАЗУ, не дожидаясь ответа сервера: ответ идёт полпинга, а вспышка должна
быть там же, где погас болт. Числа корпуса и щита потом всё равно придут
серверные.

### Прыжок к пилоту: двадцать километров

Чужой корабль — такая же точка назначения для квантового привода, как
станция. Выход считается за **20 км** от него: ближе нельзя, у пилота
есть право увидеть, кто к нему пришёл, и сманеврировать, а выход в упор —
это не прыжок, а телепорт за спину. Для сравнения: до станции привод
выходит за 40 км, до точки в пустоте — за 2.

Скорость на выходе — ноль **относительно цели**, как и везде, но у пилота
это правило значит другое, чем у планеты. Тело несёт корабль само
(гравитационный захват), поэтому рядом с ним ноль — это буквально ноль. У
чужого корабля захвата нет, и «ноль относительно него» — это его
собственная скорость. С одной оговоркой: если он сам в прыжке и идёт в
сотни раз быстрее, вектор не наследуется — лететь следом некуда.

Цель при этом живая и может исчезнуть: уйти из системы, закрыть игру,
пропасть со связью. Привод следит за этим сам и срывает прыжок, иначе тот
шёл бы к призраку — к последнему месту, где пилота видели.

### Выбор цели: почему пилот важнее планеты

Зазор до цели считается до её **края**, поэтому планета во полнеба всегда
«ближе к прицелу», чем корабль перед носом: её край накрывает прицел со
всех сторон. Пока чужие корабли просто лежали в общем списке, выбрать
пилота было нельзя вовсе — Tab неизменно брал планету за ним. Теперь
корабли идут первыми, а планета не теряется: второе нажатие Tab
перебирает то, что под прицелом, и доходит до неё.

### Чего в бою нет

- ракет и турелей: гнёзда заведены, сами они не сделаны;
- звука выстрела — нужен звуковой набор, сейчас стреляется молча;
- попаданий по планетам, станциям и грунту: болт гаснет только по
  дальности, препятствий для него нет;
- безопасных зон: стрелять можно и по пристыкованному;
- цены за гибель — ни страховки, ни потери груза.

### Какая видеокарта досталась

Контекст создаётся с `powerPreference: 'high-performance'`, но это
**просьба, а не приказ**: выбирает всё равно система. На машине с двумя
картами браузер спокойно уходит на встроенную, и тогда игра идёт вдвое
медленнее без единой ошибки в консоли — «просто тормозит».

Поэтому название карты разбирается (`gpuKind`), и при запуске игра
говорит вслух: «ИГРА ИДЁТ НА ВСТРОЕННОЙ ГРАФИКЕ · INTEL UHD GRAPHICS 630»
или «ВИДЕОКАРТА НЕ ЗАДЕЙСТВОВАНА · ПРОГРАММНЫЙ РЕНДЕР». Полное название
всегда есть в отладке (`~`), рядом с ценой кадра.

Лечится это не в игре: в Windows у браузера свой выбор карты
(Параметры → Система → Дисплей → Графика), и на настольной машине карта
вообще не участвует, если монитор воткнут в материнскую плату, а не в неё.

## Два языка

Игра идёт по-английски, русский выбирается на стартовом экране и на
странице входа — двумя кнопками, выбранная подсвечена. Выбор запоминается
(`localStorage`), и до него язык — английский.

```
js/core/lang.js      L(), выбор языка, формат чисел
js/core/lang.en.js   словарь: русская строка -> английская
```

### Ключ — сама русская строка

Никаких `hud.scanner.peers`. Причина простая: с идентификаторами исходник
перестаёт читаться — вместо надписи в коде стоит ссылка, и чтобы понять,
что нарисует прибор, надо лезть в словарь. А ещё их надо придумывать, и
придумывают их по-разному два раза подряд. С русским ключом строка видна
на месте:

```js
ctx.fillText(L('ПИЛОТОВ РЯДОМ ') + n, x, y);
```

Плата честная: поправил надпись — поправь ключ в словаре. Ровно это и
проверяется.

### Проверка читает исходники

Перевод разъезжается с игрой за неделю, если за ним не следить. Следит
проверка в `tools/test.mjs`, и следит по самим файлам: каждая русская
строка в игровых модулях обязана либо проходить через `L()`, либо лежать
в словаре. Добавить надпись молча нельзя — набор упадёт и назовёт файл.
Отдельный шаг в `tools/smoke.mjs` переключает язык на ходу и требует,
чтобы в приборах, меню, карте и справке **не осталось ни одной русской
буквы**: наполовину переведённый экран хуже нетронутого.

Не переводится намеренно: отладочный оверлей (`~`), профили железа,
ошибки сборки шейдеров — это инструменты разработки, а не игра.

### Данные и надписи — разные вещи

Названия типов планет, звёздных классов, оружия и стартовый набор пилота
лежат **по-русски в каталогах** и переводятся при показе:

```js
card.desc = info ? L(info.desc) : '';      // js/ui/map.js
```

Обёртки в самих каталогах быть не должно: они считаются один раз, при
загрузке модуля, и перевод застыл бы на языке, который был в тот момент.
По той же причине переводится при отрисовке подпись сенсорной кнопки —
раскладка считается один раз, а язык можно сменить на ходу. Проверка об
этом знает: файлы каталогов перечислены в ней отдельно.

### Что осталось по-русски

Сервер отвечает по-русски: названия товаров, заголовки подрядов, строки
ленты и сообщения об ошибках приходят из базы. Те из них, что уже есть в
игре, переведены при показе, но новые (рынок, доска подрядов) приедут
по-русски, пока язык не появится и в запросе к серверу. Проверки набора и
комментарии в коде тоже остаются русскими: это разработка, а не игра.


## Проверки

Тесты работают в Node без браузера: DOM и canvas подменяются заглушками.


Счёт на сегодня: 497 логических проверок, 222 в GL-наборе, smoke из 40
шагов, 25 сетевых, 75 серверных и 39 на сокет. Всё, чему нужна база,
вынесено в отдельные команды намеренно: `npm run check` обязан работать с
выключенным MySQL. Каждая падает, если сломать то, ради чего написана, — это
проверялось намеренно, а не предполагалось.

`tools/shot.mjs` полезен для проверки визуала Canvas-2D-пути: он показывает
фазы освещения планет, кольца, силуэт станции и створ порта прямо в консоли.

**Важное ограничение.** Пиксели WebGL автотестами не проверяются: ни Node, ни
ASCII-скриншотер не видят вывод GPU. `tools/gl.mjs` проверяет всё до драйвера —
геометрию, матрицы, отсутствие NaN в uniform, наличие draw-вызовов, рост LOD при
подлёте, — но то, как это выглядит, проверяется только глазами в браузере.
Поэтому Canvas-2D-рендер сохранён: `?renderer=2d` даёт эталон для сравнения.

## Снимок игры из настоящего браузера

```
node tools/screen.mjs                          снимок обычного полёта
node tools/screen.mjs --list                   какие сцены есть
node tools/screen.mjs --scene=approach --size=2555x1343 --out=a.png
node tools/screen.mjs --do="GAME.ship.hull = 12"
```

Приборы рисуются на Canvas, сцена — в WebGL, и до сих пор увидеть кадр
можно было только глазами человека за монитором. Отсюда была вся беда с
интерфейсом: правки делались вслепую, «покрупнее» и «поудобнее»
проверялись пересказом. ASCII-снимок ([tools/shot.mjs](tools/shot.mjs))
перехватывает вызовы Canvas 2D и для WebGL бесполезен, а числа в
`smoke.mjs` говорят, ЧТО нарисовано, но не КАК это выглядит.

Здесь всё честно: Chrome запускается без окна, открывает игру по http,
доигрывает до нужной сцены и отдаёт PNG.

**Зависимостей не прибавилось.** Chrome управляется своим протоколом
(DevTools Protocol) поверх WebSocket, который в Node 22 уже встроен, —
ни puppeteer, ни playwright ради сотни строк тянуть незачем. Сам Chrome
ищется так же, как PHP: по известным местам плюс `SOLAR_CHROME`.

**Сцена** — это кусок кода, который выполняется в странице: игра
выставляет наружу `window.GAME`, и положение, цель, режим и вид ставятся
прямо в нём. Готовые: `flight`, `approach`, `surface`, `dock`, `warp`,
`cockpit`, `map`, `menu`, `boot`. Помощники сцен — `aimAt(тело, км)`
(встать в стольких километрах от поверхности носом на цель) и
`hover(тело, км)` (зависнуть носом по горизонту — у самой земли нос на
центр тела означает нос в грунт, и корабль в него честно влетает).

Кадры двигаются вручную, шагами по 16.7 мс: почти всё в игре считается
за кадр, и снимок сразу после присваивания показал бы прошлое состояние.

Снимок идёт через программный растеризатор (SwiftShader) — в кадре об
этом честно написано «ВИДЕОКАРТА НЕ ЗАДЕЙСТВОВАНА». Для вёрстки приборов
это неважно, для оценки скорости — бесполезно.

## Точки расширения

Задел под продолжение уже заложен: `world.entities` — общий список объектов для
NPC-кораблей и снарядов, состояния в `js/game/state.js` расширяются новыми
экранами (рынок, снаряжение).

Сервер уже отвечает на всё, чего не хватало для настоящей торговли: рынок
порта, доска подрядов, кроны с лентой операций. Остался один шаг — научить
игру с ним разговаривать (см. «Сервер: подготовка к онлайну»).

Дела пилота — [js/game/player.js](js/game/player.js) — сложены так же:
кроны, трюм и задания не знают ни про корабль, ни про мир (ёмкость трюма
приходит параметром), поэтому переживут и замену корпуса, и приход этих
данных с сервера. Всё, чего не хватает для настоящей торговли, — рынок и
доска заданий на станции: список товаров просится из типов планет, которые
генератор УЖЕ расставляет (лава и камень — руда и металлы, лёд — вода и
газы, океан — продовольствие, газовый гигант — топливо), а цены — из класса
звезды и состава системы.

Галактика уже разведена под сеть. `js/game/galaxy.js` не знает про тела вовсе
и ничего не импортирует из `world.js` — он отвечает только на вопрос «где какая
звезда». Система собирается ровно в момент прибытия, и `makeSystem` принимает
не только seed, но и готовое описание: когда его начнёт присылать сервер,
меняться будет один вызов. Сам момент подмены уже вынесен наружу — привод
говорит `handover`, а что делать с памятью, решает `js/main.js`.
